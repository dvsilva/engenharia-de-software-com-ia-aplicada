# State graph

## Concept

A state graph runs a workflow as nodes that read a shared state and return partial updates, joined by fixed edges and by conditional edges that pick the next node from the state, from a start to an end. Each field of the state has a reducer that decides how an update combines with the current value, replacing it or appending to a list. The runtime works in steps, one per node execution, and stops with an error when a run needs more steps than its recursion limit, which bounds every loop. A ReAct agent is the smallest useful graph: a model node and a tools node in a loop that ends when the model answers without calling tools.

## How the course implements it

The LangChain intro of module 2 is the smallest graph in the course and calls no model. It uses **LangGraph** 1.1 for **JavaScript**, which arrives through **langchain** 1.2 without being declared, and declares its state as a **zod** object: the messages, which append through **LangGraph**'s message reducer, and the output text and a command of uppercase, lowercase, or unknown, which are replaced. From the start, an intent node copies the text of the last message to the output and sets the command to uppercase when its lowercase form contains upper anywhere, even inside a word such as supper, else to lowercase when it contains lower, else to unknown. A conditional edge with a path map goes to the uppercase node, the lowercase node, or the fallback node, which convert the whole output, spaces and accents kept, or replace it with Unknown command. Try 'make this uppercase' or 'convert to lowercase'. Every branch ends in a response node that appends the output as an AIMessage ([chat-model](chat-model.md)), and then the graph ends. Every node returns the whole state, messages included, and the message reducer recognizes the messages it already holds by id, so only the new one is appended. The graph is compiled once, when the server module loads, and served by **Fastify** ([rest-api](rest-api.md)). factory.ts and langgraph.json register it for the **LangGraph** CLI's development server, and .env.example turns on **LangSmith** tracing with LANGSMITH_API_KEY, LANGCHAIN_TRACING_V2, and LANGCHAIN_PROJECT, which **LangChain** reads by itself, so no code refers to it. With tracing on, every run uploads one trace in the background, a LangGraph run with a child run per node, and the answer stays the same.

The medical appointment lesson of module 2 routes a patient's request with **LangGraph** 1.1, which also arrives through **langchain** 1.2 without being declared, and declares its state as a **zod** 3 object through **LangGraph**'s withLangGraph and MessagesZodMeta ([schema-validation](schema-validation.md)): the messages, which append through the message reducer, and an optional patient name, intent of schedule, cancel, or unknown, professional id and name, date and time, reason, action success, action error, appointment data, and error, which are replaced. From the start, an intent node goes through a conditional edge with a path map to the message node when the state has an error, no intent, or the unknown intent, and otherwise prints ➡️ Routing based on intent: and the intent and goes to the schedule node or the cancel node, both of which go on to the message node before the end. Each node prints its own line when it starts: 🔍 Identifying intent..., 📅 Scheduling appointment..., ❌ Cancelling appointment..., and 💬 Generating response message....

In the final version, the intent node asks the model for the intent and the appointment details ([chat-model](chat-model.md)), prints ✅ Intent identified: and the intent, and returns the details as its update. When the call fails or its answer does not fit the schema, the service gives it no data, so reading the intent throws, and the node prints ❌ Error in identifyIntent node: and the error to standard error and sets the intent to unknown and the error to the exception's message. The schedule and cancel nodes first require a professional id, a date and time, and a patient name in the state ([schema-validation](schema-validation.md)), and otherwise fail the action with the messages of the missing fields, printed after ⚠️ Validation failed:. They then book or cancel through an appointment service that keeps the appointments in memory while the process lives, starting with two that fall on the day the server starts: Joao da Silva with Dr. Alicio da Silva at 11:00 UTC, and Luana Costa with Dra. Ana Pereira at 14:00 UTC the next day. A booking at an instant the professional already has fails with Horário indisponível para este profissional, a booking without a reason stores general consultation, and a cancellation needs an appointment of that professional at that instant for that patient, or fails with Agendamento não encontrado para cancelamento. Each sets the action's success and, on failure, its error, printed after ❌ Scheduling failed: or ❌ Cancellation failed:, and a booking also prints ✅ Appointment scheduled successfully and sets the appointment data: the date, patient name, reason, and professional id. The message node joins the intent, or unknown, with success when the action succeeded and error otherwise, so a question outside appointments becomes unknown_error, a scenario the prompt does not list. It sends that scenario and the professional name, date and time, patient name, and the state's error, never the action's error, prints ✅ Message generated: followed by the message, or by the whole result when there is none, and appends the message as an AIMessage. When the call fails, it prints ⚠️ Message generation failed: and the error and appends Desculpe, errei! instead. When the answer does not fit the schema, reading the missing message throws, so it prints ❌ Error in messageGenerator node: and the error to standard error and appends An error occurred while processing your request. Every node catches its own failures, so the run never throws.

In the template, no node calls the model or the appointment service: the intent node returns the state unchanged, so every question goes straight to the message node, which appends nothing, and the run ends with the question as its only message. The template's nodes return the whole state, as the LangChain intro's do, and in the final version the schedule node and the intent node's failure still do. The graph is compiled once, when the server module loads, and the route answers its whole final state ([rest-api](rest-api.md)), without the fields no node set. factory.ts and langgraph.json register it for the **LangGraph** CLI's development server, and .env.example turns on **LangSmith** tracing as in the LangChain intro.

The song highlights lesson of module 2 recommends songs in a chat at the terminal ([command-line-interface](command-line-interface.md)) with **LangGraph** 1.1, which also arrives through **langchain** 1.2 without being declared. Its state is a **zod** 3 object through withLangGraph and MessagesZodMeta ([schema-validation](schema-validation.md)): the messages, which append through the message reducer, and an optional user context, extracted preferences, summarization flag, conversation summary, and user id, which are replaced. From the start, a chat node goes through a conditional edge with a path map to a save preferences node when the state holds extracted preferences, else to a summarize node when it needs summarization, else to the end. The save preferences node goes to the summarize node or to the end by the same flag, and the summarize node goes to the end. Every turn invokes the graph with the thread id in the configuration ([conversation-memory](conversation-memory.md)), and the user as the runtime's context and as the state's user id, which in the template is the thread id itself. In the template, every node returns the state unchanged, so every run goes from the chat node to the end with the user's message as the last one, which the terminal prints as the answer. The graph is compiled without a checkpointer or a store, so every turn starts from its own message. factory.ts builds the model service ([chat-model](chat-model.md)) and the graph whenever it is called, beside the template's stub memory store whose search finds nothing, and langgraph.json registers it for the **LangGraph** CLI's development server. .env.example turns on **LangSmith** tracing as in the LangChain intro.

In the final version, the first turn also passes the user context the terminal loaded, and the graph is compiled with a **PostgreSQL** checkpointer and store, so every turn continues the thread's state ([conversation-memory](conversation-memory.md)). Every node finds the user in the runtime's context, then in the state, then as unknown. The chat node takes the user context from the state, or from the preferences store when the state has none ([sql-database](sql-database.md)), asks the model for an answer with the conversation as one User: or AI: line per message and the last message as the current one ([chat-model](chat-model.md)), and appends the answer's message as an AIMessage. It sets the extracted preferences to the answer's preferences when the answer says to save them, clears them otherwise, and sets the summarization flag when the state held at least two messages before the answer, which is every turn after the greeting. When the call fails or the answer does not fit its schema, it prints ❌ Falha ao gerar resposta: and the error, or undefined for an answer that does not fit, to standard error, and appends Desculpe, encontrei um erro. Pode tentar novamente? without touching the other fields. The save preferences node merges the extracted preferences into the store and clears them. The summarize node asks the model for a summary of every message and the previous summary, stores it, removes all messages but the last two with RemoveMessage, keeps the summary in the state, and clears the flag. When that call fails, it prints ❌ Falha ao sumarizar conversa: and the error to standard error and only clears the flag, so the thread keeps every message.

The safeguard lesson of module 2 judges every message before the model answers it ([prompt-injection-defense](prompt-injection-defense.md)) with **LangGraph** 1.1, which also arrives through **langchain** 1.2 without being declared. Its state is a **zod** object, written with zod/v3, through withLangGraph and MessagesZodMeta: the messages, which append through the message reducer, and the user, the guardrail check, null by default, and whether the guardrails are enabled, which are replaced. From the start, a guardrails_check node goes through a conditional edge with a path map to the chat node when the guardrails are disabled or the check is missing or safe, and to the blocked node otherwise, and both go to the end. In the template, every node returns the state unchanged, so every run goes through the chat node and ends with the user's message as the last one, which the terminal prints as the answer ([command-line-interface](command-line-interface.md)). In the final version, the guardrails node sets the check, and the chat node and the blocked node each append one AIMessage. When the state has no user, which only the development server sends, its chat node sets ananeri and turns the guardrails off. The program builds the graph, with its model service ([chat-model](chat-model.md)), once per run, and factory.ts and langgraph.json register it for the **LangGraph** CLI's development server.

The RAG lesson of module 2 over students runs a graph of six nodes with **LangGraph** 1.1, which also arrives through **langchain** 1.2 without being declared, over a **zod** state written with zod/v3 through withLangGraph and MessagesZodMeta ([schema-validation](schema-validation.md)). It extracts the question, plans, generates a query, and runs it, then goes back once to correct the query or to generate each further step's query, and ends with the analytical response, as [text-to-query](text-to-query.md) describes. The template's nodes return the whole state, the analytical response node with a hello world AIMessage in place of the messages, which the reducer appends. In the final version, the default recursion limit of 25 steps is what ends a run whose model calls all fail, since a failed correction leads back to the executor without counting an attempt. The server builds the graph once, beside the model service and the database service, and factory.ts builds another when it loads, which langgraph.json registers as sales_qa for the **LangGraph** CLI's development server. .env.example turns on **LangSmith** tracing.

The document analysis lesson of module 2 runs the smallest graph that calls a model, with **LangGraph** 1.1, which also arrives through **langchain** 1.2 without being declared. Its state is a **zod** object, written with zod/v3, through withLangGraph and MessagesZodMeta: the messages, which append through the message reducer, the document in base64, and an error that no node sets. One answerGeneration node runs from the start to the end. Without a document, which an empty upload leaves, it appends No document found in state without calling the model. Otherwise it prints 🤖 Sending document to multimodal model for analysis..., sends the text of the last message and the document to the model ([chat-model](chat-model.md)), prints ✅ Model: and the model the response names, and appends the answer as an AIMessage. When the call fails, it prints Error in answerGenerationNode: and the error to standard error and appends Failed to generate answer: and the error's message instead, so the run never throws. The route ([rest-api](rest-api.md)) builds the graph once and invokes it with the question as a HumanMessage and the upload in base64. factory.ts builds another instance whenever it is imported, and langgraph.json registers that export, which holds the graph beside its model service, for the **LangGraph** CLI's development server. .env.example turns on **LangSmith** tracing as in the LangChain intro.

The multiple MCP tools lesson of module 3 uses **LangGraph** 1.2 for **JavaScript** and declares its state as a **zod** object ([schema-validation](schema-validation.md)): the messages, which append through **LangGraph**'s message reducer, and an optional answer, intent, file content, file name, and error, which are replaced. The graph runs an intent parser node from the start, then the agent node unless the intent parser set an error, which ends the run. Each node prints its own line when it starts, 🧠 Intent node processing... and 🤖 Agent node processing..., and turns a failure into the error and an apology message. In the template, neither node calls the model: the intent parser returns an empty intent, the file content {}, and the file name report.json, and the agent answers Nothing yet!. In the final version, the intent parser asks the model for the intent ([chat-model](chat-model.md)) and prints 📋 Extracted intent:, 📄 File Type:, and 📄 File name:, which defaults to data. followed by the file type. An empty intent or file type prints ⚠️ Missing intent or fileType in parsed data: and fails with Invalid intent data, so the run ends with the apology before the agent node, which answers the text of its tool loop ([tool-calling](tool-calling.md)). langgraph.json also registers the graph for the **LangGraph** CLI's development server.

The Google Trends agent of module 3 declares its state the same way, with the messages and an optional trendsData, question, and keywords, which no node sets, and runs a researcher node and then a responder node. The researcher prints 🔍 Researcher processing..., asks the agent ([chat-model](chat-model.md)) to call google_trends with two keywords from the question ([tool-calling](tool-calling.md)), prints 📊 Trends data fetched via tool call even when the model called nothing, and stores the question and the agent's answer as trendsData, written as a JSON string literal with two-space indentation, which for text means the answer in quotes with its quotes and line breaks escaped. The responder prints 💬 Responder processing..., sends the question and that literal to the model under a content strategist's prompt that asks for an answer in the user's language, and appends the answer as an AIMessage. Each node catches its own failures and prints them to standard error: the researcher stores Sorry, something went wrong while fetching trends data., and the responder appends Sorry, something went wrong while generating the response.. factory.ts and langgraph.json register the graph for the **LangGraph** CLI's development server.

The LangChain lesson of module 3 keeps the multiple MCP tools lesson's state, adding an optional file type that no node sets, and drops the intent parser. Its graph runs the agent node from the start and sends it back to itself whenever it sets an error, ending only when it does not. The agent node sends the text of the last message as the user prompt and stores the agent's answer as the answer and as an AIMessage, or the error with the apology Sorry, I encountered an error while processing your request. Please try again., so a retry asks the model that apology instead of the question. A failure that repeats, such as a missing service token or model key, runs the node 25 times, the default recursion limit, and the run throws GraphRecursionError.

OpsPilot uses **LangGraph** 0.2 for **JavaScript**. ReAct, and every step of plan-and-execute, run the prebuilt ReAct agent, whose model node and tools node loop until the model stops calling tools ([tool-calling](tool-calling.md)). Plan-and-execute is a StateGraph of its own, whose state holds the request, the remaining plan, the finished steps with their results, the answer, the trace, and counters of iterations and LLM calls. The finished steps and the trace append, and everything else is replaced. Its edges go from the start to the planner, from the planner to the executor, and from the executor to the replanner, which returns to the executor until there is an answer or the step limit is reached. Without the replanner, the executor loops on itself until the plan runs out or the limit is reached, and a finishing node writes the answer. A node with nothing to do returns an empty update, and the graph is compiled for every run. From unit 4, ReAct and every step build the prebuilt agent with a system prompt, which it sends as the first message of every model call.

The recursion limits are three times the iteration limit, never below 3, for ReAct, three times the step limit, never below 3, for each step's agent, and five times the step limit, never below 10, for plan-and-execute. With a limit of 3, a ReAct run calls the model, runs the tools, and calls the model again, and fails before running the tools that second answer asks for. ReAct turns that failure into its iteration-limit answer ([reasoning-strategies](reasoning-strategies.md)), while a step that fails it ends the whole plan-and-execute run with an error.

Unit 6 runs every chat turn through one production graph, compiled for every turn, whose state holds the message, the user, the conversation id, the request id and its creation time, the route the request forces, the built context, the chosen route, the answer, the trace, the strategy's metrics, and the router's LLM calls. The trace appends, and everything else is replaced. From the start, the contexto node summarizes the history when it is due, loads the window and the summary, recalls the memories, builds the context, and stores the user's message ([context-management](context-management.md)), and the roteador node picks the route ([reasoning-strategies](reasoning-strategies.md)). A conditional edge with a path map goes to the node named after the route, react, planExecute, or reflect, which runs that strategy on the built context and stamps its own name as the node of every event the strategy returns, and every strategy node goes to the resposta node and then to the end. The resposta node stores the answer, adds a fallback event when the reserve model answered ([model-routing](model-routing.md)), assembles the metrics, and audits and logs the turn ([agent-observability](agent-observability.md)). Every event of a chat trace carries the node that produced it: a summarize event contexto, the route event roteador, the strategy's events the route's name, and a fallback event resposta. Run alone, as in the arena, the strategies stamp react, plan-and-execute, and reflect:react, which the arena never prints.

Unit 9 adds a team node for the team route, which goes to resposta like the others but keeps the node that each event already carries, the supervisor or the role that produced it. The team is a StateGraph of its own ([multi-agent-orchestration](multi-agent-orchestration.md)), compiled for every turn, whose state holds the request, the blackboard, the delegation count, the latest brief, the next step, the answer, the trace, and the LLM calls. The blackboard and the trace append, the LLM calls add up, and everything else is replaced. A conditional edge with a path map goes from the supervisor to the analista, planejador, executor, or done node, every role goes back to the supervisor, and done goes to the end. Its recursion limit is 34, three steps per delegation plus ten, so the cap of eight delegations always closes the run before the limit does.

## What usually goes wrong in other languages

- **LangGraph** is published for **Python** and **JavaScript** only, and **LangGraph4j** follows it on **Java**. Other targets write the loop and the state transitions by hand and count one step per node execution, so the limits fail at the same point.
- **Python**'s prebuilt ReAct agent, unlike the **JavaScript** one this module uses, ends with "Sorry, need more steps to process this request." instead of failing when its steps run out. The tested transcription builds the two-node graph from ToolNode and tools_condition, which fails with GraphRecursionError at the same step as the original.
- A state field without a reducer keeps the last value written. **Python** declares the appending fields with Annotated, using operator.add for plain lists and add_messages for messages.
- A reducer that only concatenates, such as operator.add, duplicates the messages that the nodes of the LangChain intro, the medical appointment lesson, the song highlights template, the safeguard template, and both versions of the RAG lesson over students return with the whole state. Transcriptions return only the new message. The LangChain intro's route answers only the output, the RAG lesson's only the answer and the follow-up questions, and the song highlights chat and the safeguard chat print only the last message, so their cases cannot tell, while the medical appointment lesson answers the messages, and its cases expect each one once.
- The song highlights lesson's edges check the extracted preferences before the summarization flag, so a turn with both saves the preferences and then summarizes. Its edge functions name the end end, which the path map turns into the graph's end.
- In the song highlights final version, a field a node returns as undefined is cleared, as the save preferences node clears the preferences, while a field it leaves out keeps its value from earlier turns, as after a failed chat call. A returning user's context arrives in the first turn's input and stays in the thread's state, so every later turn sends the context loaded at startup even after the summaries rewrite the store, while a new user's context is read from the store on every turn.
- The summarize node removes messages by id with RemoveMessage, which **Python**'s add_messages understands too. A graph written by hand keeps the last two messages instead.
- **LangGraph4j** copies the state between steps through a serializer, **Java** serialization by default, which **LangChain4j**'s messages do not support, so the first step fails with NotSerializableException. LC4jStateSerializer from **langgraph4j-langchain4j** handles them, and **LangGraph4j** also needs an **SLF4J** binding, such as **slf4j-nop**, or it prints a warning to standard error.
- The LangChain intro's command is a substring test on the lowercase text, upper first, never a word match, so supper counts as upper and flowers as lower. Its case conversion is **JavaScript**'s full Unicode mapping without a locale, which turns ß into SS. **Java** matches it with Locale.ROOT, while **Go**'s strings.ToUpper and **C#**'s ToUpperInvariant keep ß, which no case checks.
- The medical appointment lesson answers the graph's state as it is, so each message reaches the client in the serialized form of **LangChain** for **JavaScript**: lc 1, type constructor, an id of langchain_core, messages, and the class name, and kwargs with the content, empty tool_calls and invalid_tool_calls for an AIMessage, empty additional_kwargs and response_metadata, and the id the message reducer generated, a UUID version 4. **LangChain** for **Python** serializes under langchain, schema, messages, adds the type to kwargs, and leaves the empty fields out, so every target, **Python** included, writes that JSON itself. The state fields no node set are left out, never written as null, and so are the unset details the message node sends the model.
- The medical appointment lesson's action fails with the messages of every missing field, in the order professional id, date and time, patient name, joined by a comma and a space. Its appointment service compares instants, never the text of the date.
- The lines that start with ➡️ and ⚠️ have two spaces after the emoji, which the cases compare exactly.
- The Google Trends agent hands the researcher's answer to the responder as a JSON string literal, which the cases compare exactly inside the prompt. **Python**'s json.dumps needs ensure_ascii off to keep the accents unescaped, as JSON.stringify does.
- **LangSmith** tracing comes from environment variables alone in **LangChain** for **Python** and **JavaScript**. Other targets, **LangGraph4j** included, trace nothing by themselves, so a transcription leaves it out, and the cases run with it off.
- The document analysis lesson's node tests the document for truthiness, so an empty upload, whose base64 is the empty string, counts as no document. A target that tests only for null or None sends the model an empty data URL instead.
- The LangChain lesson's loop back to the agent sets no limit of its own, so it ends at **LangGraph**'s default of 25 steps, which **Python**'s **LangGraph** shares. A loop written by hand stops after the node's 25th run and throws, since the route answers 500 only when the run fails, and retries with the last message, the apology, not the first question.
- The prebuilt agent names its nodes agent and tools, and the conditional edge after the model goes to the tools only when the last message has tool calls.
- OpsPilot's production graph names its nodes in Portuguese and its strategy nodes after the routes, and those names reach every trace event, which the cases compare exactly. A target without **LangGraph** runs the nodes in order and concatenates their events: the summarize event, the route event, the strategy's events, and the fallback event. The team route's events keep the supervisor and role names instead.
- The team graph's LLM calls add up across nodes while its other counters replace, so a target whose state has one merge rule for every field either loses the roles' calls or adds the delegation count to itself.

## How close common targets get

| Target                            | Fit               | Library                                                                   |
| --------------------------------- | ----------------- | ------------------------------------------------------------------------- |
| **Python**                        | Direct equivalent | **langgraph**, building the ReAct graph from ToolNode and tools_condition |

| **Java**                          | Direct equivalent | **LangGraph4j**, with **langgraph4j-langchain4j** for messages            |
| **Go**                            | Substitute        | A loop over a state struct, counting steps, written by hand               |
| **Rust**                          | Substitute        | A loop over a state struct, counting steps, written by hand               |
| **C#**                            | Substitute        | A loop over a state record, counting steps, written by hand               |
| **C++**                           | Substitute        | A loop over a state struct, counting steps, written by hand               |
