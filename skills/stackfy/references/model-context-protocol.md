# Model Context Protocol

## Concept

The Model Context Protocol (MCP) lets one program offer tools, and also resources and prompts, to any agent that speaks it, such as **GitHub Copilot**, **Cursor**, or **Claude**. The client and the server exchange JSON-RPC 2.0 messages. Over the stdio transport, the client starts the server as a child process and both write one JSON message per line, the client on the server's standard input and the server on its standard output, so standard output belongs to the protocol and diagnostics go to standard error. A session starts with an initialize request, answered with the server's name, version, and capabilities, followed by an initialized notification. Then tools/list describes each tool by name, description, and the JSON Schema of its input, and tools/call runs one tool and answers content blocks, usually text, flagged with isError when the call failed. A tool may also declare the JSON Schema of its output and answer the same result as structuredContent beside the text. resources/list and resources/read hand out read-only content by URI, and prompts/list and prompts/get describe prompt templates with their arguments and render one into messages. The client ends the session by closing the server's input, and the server exits. A client may hold sessions with several servers at once, each started with its own command and environment, and hand all of their tools to one agent as if they were its own. Over the streamable HTTP transport, a long-running server takes every message as a POST to one path, answers initialize with a session id in the Mcp-Session-Id header, which every later request carries, and answers each request either as JSON or as server-sent events.

## How the course implements it

The Grafana MCP lesson of module 1 hands an assistant a third-party server instead of writing one. Its compose file runs mcp/grafana over streamable HTTP on port 8000, in front of the **Grafana** that queries the lesson's **Prometheus**, **Loki**, and **Tempo** ([telemetry](telemetry.md)), and the README registers it for **Windsurf** at http://localhost:8000/mcp. Its tools include query_prometheus, query_loki_logs, list_datasources, and tools for dashboards, alerts, and incidents, plus **Tempo**'s own tools, such as tempo_traceql-search, which it proxies from the MCP server **Tempo** runs. Each query tool takes a datasource's uid and a PromQL, LogQL, or TraceQL query and answers the results as JSON text. The lesson's prompts ask the assistant to call them in turn and correlate what they find ([coding-agent-harness](coding-agent-harness.md)).

The safeguard lesson of module 2 declares **@langchain/mcp-adapters** 1.1 and @modelcontextprotocol/server-filesystem, and its template imports neither. Its final version starts the filesystem server over stdio through npx, with the working directory as its only allowed folder, the first time the chat agent runs, and hands all of its tools to that agent whatever the user's role, which is what a member's prompt injection reaches when the guardrail is off ([prompt-injection-defense](prompt-injection-defense.md)).

The multiple MCP tools lesson of module 3 is a client. It declares **@langchain/mcp-adapters** 1.1, whose MultiServerMCPClient starts MCP servers over stdio, lists their tools, and turns them into **LangChain** tools for the agent ([tool-calling](tool-calling.md)). The template's MCP service returns no tools. The final version starts two third-party servers through npx the first time the agent needs tools: the **MongoDB** MCP server, mongodb-mcp-server at @latest, which MDB_MCP_CONNECTION_STRING points to mongodb://localhost:27017/dataprocessing, and @modelcontextprotocol/server-filesystem, allowed to read and write only the working directory. The agent gets the **MongoDB** tools, then the filesystem tools, then the lesson's own csv_to_json. Every logging notification prints as the server's name in brackets followed by its data, and the sessions are never closed, so the servers exit with the program. **MongoDB** 8 runs in **Docker** from the lesson's compose file, beside a **mongo-express** the program never uses.

The Google Trends agent of module 3 starts only the filesystem server, the same way and at the same moment, and offers its tools before the lesson's own google_trends to both nodes of its graph ([tool-calling](tool-calling.md)). The server's notices reach standard error, and no case expects the model to call it.

The MCPs from scratch lesson of module 3 builds a server with the official SDK. Its template declares **@modelcontextprotocol/sdk** 1.27 and **zod** 3 but imports neither, and only runs, from a plain entry point, the encryption service the server will offer ([symmetric-encryption](symmetric-encryption.md)). The final version, @erickwendel/ciphersuite-mcp at version 0.0.1, connects a high-level server through the stdio transport and then writes Encrypt MCP Server running on stdio to standard error. Its tools, encrypt_message and decrypt_message, take the message or the iv:ciphertext text with the passphrase as encryptionKey, declare an output schema ([schema-validation](schema-validation.md)), and answer each result twice, as a text block holding the bare message and as structuredContent under encryptedMessage or decryptedMessage. A decryption that throws becomes a result with isError whose text starts with Failed to decrypt message! and ends with the library's message after Error details:. The encryption://info resource, named after its URI, reads as plain text that describes the algorithm, and encrypt_message_prompt takes the same two arguments as encrypt_message and renders one user message asking the agent to call it. Its tests connect a client through the SDK's stdio client transport, and .vscode/mcp.json registers the server for **Copilot**.

The legacy API lesson of module 3 offers an existing REST API to agents. Its template is a server named @erickwendel/ew-customers-mcp at version 0.0.1, connected through the stdio transport, that writes Customers MCP Server running on stdio to standard error and registers nothing yet, so it declares no capabilities and answers every listing with Method not found. The final version registers five tools over the customers API of [rest-api](rest-api.md), which it always calls at http://localhost:9999/v1 through a client and a service ([layered-architecture](layered-architecture.md)):

- list_customers answers the API's array as indented JSON text and as structuredContent under customers.
- get_customer takes an optional \_id, name, and phone. With an \_id, it asks the API for that customer and answers what the API returns, whose key is id, or null on a 404. Otherwise it lists the customers and keeps the first, in the API's name order, whose every given field contains the given text, case-sensitive, or null. It answers the customer as JSON text and under customer.
- create_customer posts the name and the phone and answers the API's body as JSON text and as structuredContent.
- update_customer takes a required \_id with an optional name and phone and puts the given fields to the API, and delete_customer deletes by \_id. Both answer the API's message as text, or empty text without one, and its whole body as structuredContent, whatever its status.

Every tool declares an output schema built from the lesson's **zod** schemas ([schema-validation](schema-validation.md)), and a thrown error, such as an unreachable API, becomes a result with isError whose text is Failed to list customers. Error: and the message, whichever tool failed. The customers://api-info resource, named after its URI, reads as plain text that gives the base URL, the five endpoints, and the customer's shape, and find_customer_prompt takes the same optional \_id, name, and phone and renders one user message asking the agent to use get_customer or list_customers, followed by Query: and the given arguments as JSON. Its tests call the tools against a running API.

The API security lesson's template keeps that server, its resource, and its prompt, and secures its calls ([api-access-control](api-access-control.md)): it requires SERVICE_TOKEN, sends it as a bearer, and answers every failing status, the API's refusals included, with Failed to, the tool's action, and the error, as a structuredContent message beside isError true. Every tool's output schema is now the mutation answer, so a get_customer that finds nothing breaks it with a null customer, and the SDK answers with isError and its output validation error. create_customer is described as Create a new customer, its phone as Phone number of the customer, and delete_customer's \_id as MongoDB ObjectId of the customer to delete. The final version keeps the template's server unchanged. The publishing lesson keeps it too and ships it as the package @erickwendel/customers-mcp, which **Copilot**'s mcp.json starts through npx instead of from the source ([package-publishing](package-publishing.md)), while the server still introduces itself as @erickwendel/ew-customers-mcp at 0.0.1.

The LangChain lesson of module 3 hands that server to the multiple MCP tools lesson's agent. The first time the agent needs tools, it starts two servers through npx: @erickwendel/ew-customers-mcp at @latest from the public registry ([package-publishing](package-publishing.md)), with SERVICE_TOKEN as the only variable it adds to the server's environment, and @modelcontextprotocol/server-filesystem, allowed only the data folder of the working directory. The published server is the publishing lesson's, with each tool's output schema written inline, so get_customer may answer a null customer, and a search by name or phone that ignores case. Without SERVICE_TOKEN, building the servers' configuration throws before either starts, and a server that fails to start prints ❌ MCP server failed to connect: with its name and the error and ends the program with 1. Its ✅ MCP server connected: hook waits for an initialized notification, which only clients send, so it never prints.

From unit 3, OpsPilot also provides tools instead of only consuming them. Its MCP server uses the official SDK, **@modelcontextprotocol/sdk** 1.30, with a high-level server named opspilot at version 0.1.0, the package's version, connected through the stdio transport and started by npm run mcp. It opens and seeds the same SQLite database as the chat API ([sql-database](sql-database.md)) and registers exactly three tools, list_alerts, open_incident, and resolve_incident, which share their **zod** schemas, descriptions, and functions with the agent's tools ([tool-calling](tool-calling.md)). The agent-only tools, list_incidents, consultar_runbook, and check_provider_status, stay out of the catalog. Each call answers a single text block with the text the agent's tool would return, and the SDK checks the arguments against the shared schemas first, so a missing status lists firing alerts and sev2 opens a high incident.

Once connected, the server writes "opspilot MCP server: pronto (stdio)" to standard error, and a unit test fails if any MCP source writes to standard output. The project registers the server for **VS Code** and **Cursor** in their mcp.json files, so **Copilot** can open an incident that the chat API then finds in the database, the lesson's circular proof. Unit tests connect a client through the SDK's in-memory transport pair. Unit 4 leaves the server unchanged, so the memory and its forget_preference tool stay out of the catalog.

## What usually goes wrong in other languages

- The Grafana MCP lesson's README registers the server with type sse, while the container speaks streamable HTTP, and its snippet lacks a closing brace. Clients register it as a streamable HTTP server at the same address. The server answers 400 Invalid session ID to any request without the session id from initialize, and answers tool calls as server-sent events even to a client that also accepts JSON.
- A single print to standard output corrupts the session. **Python**'s print, **Go**'s fmt.Println, and **Rust**'s println! all write there, so diagnostics use standard error, and the cases require every line of standard output to be a JSON message.
- Several requests in flight may be answered out of order, even by the original, so clients pair answers with requests by id. The runner sends one request at a time and waits for its answer.
- Invalid arguments and unknown tools come back as a tool result with isError from the TypeScript SDK versions the course uses, while **rmcp** answers an unknown tool with a JSON-RPC error with code -32602, and other SDKs and older versions answer both that way. Both are valid, and the cases accept either.
- SDKs list tools, and a prompt's arguments, in their own order: the TypeScript SDK keeps the order of registration, while **rmcp** sorts both by name. Clients treat them as sets, so the cases compare these listings in any order.
- Structured output helpers usually write the structured value as JSON into the text block too, as **rmcp**'s Json wrapper does, while the MCPs from scratch lesson's text block holds the bare message, and the legacy API lesson's list_customers and get_customer write the array or the customer alone, without the key that wraps it in structuredContent. The tested **Rust** transcription builds the result itself and declares the output schema in the tool's attribute.
- The MCPs from scratch lesson names its arguments and fields in camelCase, such as encryptionKey and encryptedMessage, so a **Rust** transcription renames its fields with serde's rename_all, and a **Python** FastMCP tool takes parameters with those exact names.
- The MCPs from scratch lesson's README lists a decrypt_message_prompt that the server never registers. Transcriptions follow the code, and the cases expect encrypt_message_prompt alone.
- Failures the tool handles itself, such as an unknown incident in OpsPilot, or the legacy API's answers to an update that changes nothing, a missing phone, or a malformed id, are ordinary results without isError, exactly what the agent reads. Only a call that throws sets isError.
- The legacy API lesson's server always calls http://localhost:9999/v1, so its cases run the legacy API there, built from the module's compose file, the API security and publishing lessons' MCP cases put the replay of the API there, as the LangChain lesson's cases do beside the model's answers, and a transcription keeps that address.
- The LangChain lesson's onInitialized hook never fires, and a transcription that prints a line once each server connects adds output the cases do not expect.
- **Go**'s go-sdk infers schemas that forbid additional properties from struct types and checks every result against its output schema, so the tested transcription of the legacy API lesson writes the lesson's schemas as jsonschema-go values and passes the API's answers through as raw JSON. go-sdk writes the structured value as the text block unless the handler sets one, and turns an error the handler returns into a result with isError and the error's text.
- get_customer answers the API's object for an \_id, keyed id, and a listed document for a search, keyed \_id, so a transcription passes both through as maps instead of decoding them into one customer type, which would lose one of the keys.
- The TypeScript SDK checks every successful result against the tool's output schema with **zod**, which ignores unknown keys, so get_customer fails with isError when the API answers a malformed \_id without a name and a phone. The listed JSON Schemas forbid additional properties, so a client that validates results, as the TypeScript SDK's does after listing the tools, also rejects a customer found by \_id, whose id the schema does not name. The cases compare what the server sends.
- find_customer_prompt writes the arguments as compact JSON in the order \_id, name, phone, which **zod**'s parse gives and which is also alphabetical, as a **Go** map marshals. **Python**'s json.dumps adds spaces unless given compact separators.
- An empty list reads [] in the text and in the structured content, while a nil slice in **Go** marshals to null.
- The **Python** SDK's low-level server lists the schemas it is given exactly, but checks neither the arguments nor the results against them, so the tested transcription of the API security lesson's template checks both with **jsonschema** and answers a failure with isError, as the TypeScript SDK does.
- Deleting a well-formed id that matches nothing hangs, because the legacy API never answers it and the original's fetch has no timeout. No case sends it.
- The argument normalization lives in the shared schemas. **Python**'s FastMCP builds its schema from the function signature, so a Literal type keeps the enum the clients read and a BeforeValidator maps the pager aliases and the missing status before validation.
- The **Python** SDK reports its own version, or none, unless the server passes one, so a transcription sets 0.1.0 itself. It also logs every request to standard error, which the cases allow.
- Each SDK words its schemas differently, adding $schema, titles, defaults, or additionalProperties. The cases check the names, descriptions, property types, enums, minimum lengths, property descriptions, and required fields of every tool's input, and of its output when it declares one.
- The server must exit when its input closes. The original does, and a server kept alive by a thread or an open handle is stopped by the runner and fails the exit check.
- The TypeScript SDK's stdio client hands a server only HOME, LOGNAME, PATH, SHELL, TERM, and USER from its own environment, plus the variables the server declares, and lets the server's standard error through. **Go**'s exec.Cmd passes the whole environment, or only the Env it is given, and discards standard error, so the tested transcription sets both, which keeps npx reachable and the **OpenRouter** key away from the servers. **rmcp**'s child process transport runs a **Tokio** Command, which passes the whole environment unless cleared and lets standard error through, so the tested **Rust** transcription of the safeguard lesson clears it and passes the same six variables.
- mongodb-mcp-server at @latest changes its tools and wording between releases, and its answers carry generated ids. Its tools take a connectionId, which is preconfigured when the connection string comes from the environment.
- **langchain-mcp-adapters** for **Python** hands out tools that only run asynchronously and opens a session for each listing and each call, so the agent runs on asyncio. The tested transcription keeps one event loop in its own thread for every request, because the OpenAI client stays bound to the loop that first used it.
- **LangChain**'s adapter checks the arguments against each server's schema before calling it and hands the agent results that carry structured content as JSON, while other clients pass the arguments through and keep the text blocks. The cases compare no result of these servers, so both pass.

## Tolerance

OpsPilot's server answers deterministically, except for incident ids, which the cases check by shape (inc-, the epoch in milliseconds, a dash, and four hex digits). The protocol version the server answers is not compared, and errors are accepted in either form above. The cases of the multiple MCP tools lesson, the Google Trends agent, and the safeguard lesson's final version check the servers' tools by name and compare none of their results, apart from the empty listing and the count of inserted records that the first lesson's tool log shows, and the package.json that the safeguard agent reads, whose name and version the cases find in the tool message whether it holds the file's text or the MCP text block around it. The Grafana MCP lesson's case repeats each tool call until its answer shows the app's telemetry, and checks the answers by pattern, since they are server-sent events. The MCPs from scratch lesson's cases compare its listings, its resource, and its rendered prompt exactly, apart from the order of the listings, check every encryption by shape, decrypt ciphertexts recorded from the original exactly ([symmetric-encryption](symmetric-encryption.md)), and check a failed decryption by the lesson's text up to Error details:, since the library's message varies. The legacy API lesson's cases run the final version against the original API and an empty **MongoDB**, check ids by shape and later answers against the ids returned, compare texts that hold JSON by value, so spacing and key order are free, compare the prompt's arguments by name and description and get_customer's nullable output by its description, since SDKs write optional and nullable values their own way, and accept the template's listings as Method not found or as empty lists. The API security and publishing lessons' MCP cases replay the API instead, with fixed ObjectIds, so they compare every answer exactly, and accept a get_customer that finds nothing as a result with isError, any JSON-RPC error, or a null customer from SDKs that do not check their output. The LangChain lesson's cases start both servers through npx and replay the API on port 9999 beside the model, so they compare every call the published server makes with its bearer, find the API's answers in the program's output, and read the file the filesystem server writes.
