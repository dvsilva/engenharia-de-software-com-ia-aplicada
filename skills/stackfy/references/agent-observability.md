# Agent observability

## Concept

An agent decides by itself which tools to call and what to answer, so operating it needs a record of why it did what it did. Every request gets an id that travels in the answer, in a header, and in every log line, so one turn can be followed end to end. Logs are structured, one JSON object per event, and carry only metadata such as status, route, latency, and token counts, never the user's message, the answer, or the trace, which may hold sensitive data. The full trace of a turn goes to an audit store instead, where a later request can read why a past decision was made, and aggregates over a time window show volume, errors, tokens, cost, and latency percentiles by route and by model. A human approval bounds the agent's autonomy: a request marked as risky is held and answered with an approval id, and runs only when someone approves it. Unlike the **OpenTelemetry** signals of [telemetry](telemetry.md), which instrumentation emits for any service, these records are the agent's own and written by its code.

## How the course implements it

OpsPilot's unit 7 teaches this layer, and units 6 and 8 hold the same server code. The unit's notes also plan a token budget per conversation answered with 429, a price table per model, a contract of four autonomy levels, and a pause inside the graph through **LangGraph**'s interrupt when a destructive silence_all_alerts tool is called. The code has none of them, so transcriptions leave them out: the approval is decided before the request runs, and the stats price every paid model at one flat rate.

Every POST /chat and POST /approvals mints a random version 4 UUID before validating anything, sends it as the X-Request-Id header, and puts it first in the body as requestId ([rest-api](rest-api.md)). A logger writes one compact JSON line per event to standard output: ts in epoch milliseconds, level (info, warn, or error), event, and then the metadata in the order the code passes it, leaving out undefined values, the keys message, answer, trace, content, payload, toolArgs, body, and prompt, and anything that is not a string, a number, a boolean, or null. The chat route logs chat_request_start with the request id once the body parses, then a warn chat_request_error with the httpStatus, 400 or 422, and the errorCode, validation_error or unknown_strategy, for an invalid body, or chat_request_end with httpStatus 202 and the approvalId for a held request. A turn's resposta node logs chat_request_end with the request id, node resposta, type done, the route, httpStatus 200, the latency, the LLM calls, promptTokens or null, traceEventCount, and modelUsed ([state-graph](state-graph.md)), and a failed turn logs an error chat_request_error with only the request id and the errorCode, such as conversation_not_found or model_unavailable. A body that does not parse fails before the route, so it logs nothing and gets no request id.

The resposta node also audits every turn that finished, in two tables of the same SQLite file ([sql-database](sql-database.md)): the request, with its creation time from the handler, its finish time, status success, httpStatus 200, the conversation, the user, and the metrics, plus copies of the latency, the LLM calls, the route, and the model, and the trace, one row per event in order. A failed turn, a held request, and a denial are never stored. GET /requests/:id answers the request record and its trace, the same events the chat answered, 404 request_not_found for an unknown id, and 400 for an id that is not a UUID. GET /stats reads the requests created within since, digits followed by ms, s, m, h, or d in any case, 24h by default, and answers since as given, total, errors (a status of error or an HTTP status from 400), tokens (the sum of the positive promptTokens), costUsd, latency with p50 and p95, and byRoute and byModel, each a map to its own total, errors, tokens, and costUsd. The cost is 0.15 dollars per million prompt tokens, or zero for a model whose name contains :free, and every costUsd is rounded to six decimals on its own. The percentiles are nearest-rank over the stored latencies, which are the strategy's own, not the HTTP request's, and null when nothing matches. A since of zero passes the schema and answers 400 validation_error with the message invalid since duration.

A chat body with awaitHumanApproval true is validated, strategy included, and then held in memory instead of running: the server answers 202 with the request id, the conversation id or null, and pending, made of a new approval id, a summary, and the creation time. The summary is the message trimmed, or its first 239 UTF-16 units followed by … when it is longer than 240. POST /approvals/:approvalId takes a decision of approve or deny and a non-empty userId, and removes the held request before deciding, so a second decision answers 404 approval_not_found. A denial answers 200 with Ação cancelada pelo plantonista. as the answer, a trace of that single answer event from the approval node, metrics of zero LLM calls and the latency, and the held conversation id, and runs nothing. An approval runs the held message, user, strategy, reflect flag, and conversation id as a chat turn under the approval's own request id, logging approval_approve with the approval id and the held request's id as priorRequestId, preceded by a warn approval_user_mismatch when the approving user differs, which never stops it. Held requests are lost on restart.

Unit 8's War Room puts the trace and the approvals on a page ([component-framework](component-framework.md)). Ver raciocínio lists a turn's trace events with their type, content, node, and tool, and from unit 9 a handoff's destination after para:, between its type and its brief. Its Exigir aprovação checkbox holds every message it sends, and the card of a held request shows the API's summary and sends Aprovar or Negar as the user war-room, after which the answer of the run or of the denial joins the conversation.

The AIOps labs of module 6 bound autonomy inside the tools themselves ([tool-calling](tool-calling.md)). The guardrails lab's executar_fix_k8s_com_seguranca takes the manifest the safety SRE wrote ([agent-crew](agent-crew.md)) and prints, each after a blank line, --- 🛡️ GUARDRAIL DE SEGURANÇA ATIVADO ---, 🤖 IA sugere o seguinte manifesto: followed by a blank line and the manifest, and --- ⚙️ EXECUTANDO SIMULAÇÃO (DRY-RUN) --- with a line saying a simulated dry run of deployment.apps/checkout-api succeeded ([infrastructure-as-code](infrastructure-as-code.md)). It then asks, after a blank line, 🚨 VOCÊ APROVA A APLICAÇÃO DESTA CORREÇÃO EM PRODUÇÃO? (sim/nao): on standard input ([command-line-interface](command-line-interface.md)). sim, trimmed and in any case, answers 🚀 SUCESSO: Alteração aplicada no cluster após aprovação humana., and anything else 🛑 CANCELADO: O Engenheiro rejeitou a alteração sugerida pela IA. The ChatOps lab's execute_terraform takes a command and a manager_password, None by default. A command with destruir, apagar, or destroy in its lowercase text answers 🛑 BLOCKED: Critical action detected! Provide the correct manager_password to proceed. unless the password is exactly GESTOR-APROVA, which answers ✅ APPROVED: Human-in-the-loop validated. Terraform executed successfully. Any other command answers ✅ SUCCESS: The command '<command>' was executed (Low impact). Nothing is applied in either lab: the approval and the password only choose the text the model reads.

The TrialForge gateway of module 8 ([ai-gateway](ai-gateway.md)) keeps its audit trail in audit-trail.jsonl beside the program, appending one JSON object per line and never truncating it, which the lesson ties to 21 CFR Part 11, and the folder ships the trail of a reference run. Every record starts with timestamp, the current time in ISO 8601, followed by the decision's fields in a fixed order. A cache hit records id_requisicao, pergunta, intencao, cache_hit true, similaridade_cache, and status_final respondido_via_cache. A draft sent to the approval gate first records id_requisicao, pergunta, intencao, status_final aguardando_aprovacao, and motivo_gate, before the question is asked, so a pending request survives a crash. Every request that reached a model then records id_requisicao, pergunta, intencao, cache_hit false, modelo_usado, indice_usado, iteracoes_agentic, esgotou_agentic, confianca_rag, gate_acionado, aprovado, and status_final aprovado or rejeitado. An unhandled error records only erro and status_final falha_tecnica. After its five questions, the gateway reads the whole trail back, leaves out the pending records, takes the last five, and prints its counts and fourteen checks of their decisions, such as the paraphrase hitting the cache and the CSR synthesis taking the expensive model and the gate, with a total, raising when any fails. The checks compare decisions, never the generated text.

The tiering prototype of the enterprise architecture lesson keeps its trail the same way, in audit-trail-tiering.jsonl, which the folder ships with two reference runs, without request ids or pending records. A request blocked by its study's budget records estudoId, pergunta, and status_final bloqueado_por_orcamento. Every other request records estudoId, pergunta, intencao, tier_usado (Tier 1, Tier 2 (escalado), or Tier 2), escalou_cascata, confianca_busca, confianca_resposta, null for a CSR synthesis, gasto_acumulado, orcamento_limite, aprovado, and status_final aprovado or rejeitado, once the approval is answered. An unhandled error records erro and status_final falha_tecnica, except in the volume mode, which also verifies nothing. After its four requests, the prototype reads the whole trail back, takes the last four records, and prints seven checks of them with a total, raising when any fails: the cheap tier resolving the routine question, the off-topic question escalating, the CSR synthesis taking the expensive tier without the cascade and being approved, estudo-B being blocked, and both routine records carrying the answer's confidence as a number.

## What usually goes wrong in other languages

- Each log line is compact JSON with ts, level, and event first and the metadata after them in the original's order, which the cases compare exactly, apart from the times, the ids, and the latencies. **Python**'s json.dumps needs separators without spaces, and logging libraries add fields of their own, such as **Go**'s slog with time and msg or **Python**'s logging with its formatter, so transcriptions write the line themselves, to standard output.
- promptTokens is null in the log line when the turn has none, while the chat answer leaves it out.
- The body carries requestId only for a held request, a denial, and a finished turn, while the X-Request-Id header carries it on every chat and approval answer, errors included.
- The audit trace leaves absent fields out instead of storing them as null.
- Nearest rank takes the element at the ceiling of p percent of the count, minus one, from the sorted latencies, so with two values p50 is the smaller one. **NumPy**'s percentile interpolates unless its method is inverted_cdf, and **Python**'s statistics.quantiles differs too.
- The approval removes the held request before checking anything else about the decision, and the turn it runs fails or succeeds like any chat turn, so a failed approval cannot be retried.
- A held request's conversation id must be a UUID, but whether that conversation exists is checked only when the approval runs it.
- The guardrail asks inside the tool, while the crew waits for its result, so the question and the manifest appear in the middle of the run's output, and the answer it reads decides only the tool's text. The cases type sim or nao after the question appears.
- execute_terraform compares the password exactly but looks for the destructive words in the lowercase command, so DESTROY is held as well.
- The gateway's **JavaScript** version writes compact lines with times such as 2026-08-05T01:54:55.309Z, while **Python**'s json.dumps puts a space after each colon and comma and its isoformat writes microseconds and +00:00. Both keep accents, dashes, and < unescaped, which **Python** needs ensure_ascii=False for, **C#**'s System.Text.Json JavaScriptEncoder.UnsafeRelaxedJsonEscaping, and **Go**'s encoding/json an encoder with SetEscapeHTML(false).
- The gateway verifies the trail it reads from the file, which the shipped reference run already fills, so its counts grow with every run while its checks look only at the last five finished requests, and a run that leaves fewer than five behind fails them.

## How close common targets get

Every target can mint UUIDs, write JSON lines, and query SQLite, so every target is a direct equivalent:

| Target                            | Fit               | Library                                                                                   |
| --------------------------------- | ----------------- | ----------------------------------------------------------------------------------------- |
| **Python**                        | Direct equivalent | json with compact separators, uuid4, sqlite3, and a dict for held requests                |
| **JavaScript** and **TypeScript** | Direct equivalent | JSON.stringify, crypto.randomUUID, node:sqlite, and a Map                                 |
| **Go**                            | Direct equivalent | encoding/json with ordered structs, **google/uuid**, **modernc.org/sqlite**, and a map    |
| **Rust**                          | Direct equivalent | **serde_json** with ordered structs, **uuid**, **rusqlite**, and a HashMap behind a Mutex |
| **C#**                            | Direct equivalent | Utf8JsonWriter, Guid.NewGuid, **Microsoft.Data.Sqlite**, and a ConcurrentDictionary       |
| **Java**                          | Direct equivalent | **Jackson** with ordered maps, UUID.randomUUID, **sqlite-jdbc**, and a ConcurrentHashMap  |
| **C++**                           | Direct equivalent | **nlohmann/json**'s ordered_json, SQLite's C API, and a UUID built from random bytes      |

The guardrails of module 6 need only a prompt on standard input and text comparisons, which every target has.

## Tolerance

Request ids, approval ids, conversation ids, times, and latencies vary, so the cases check their shape and how they are reused: the header repeats the body's request id, the log lines of a request share one id, an approval runs under a new id, and the audit answers the chat's own metrics and trace. Tokens and costs follow from replayed usage, so they are compared exactly, while the percentiles are checked as numbers. The gateway's trail is compared record by record in either original's spacing, with the shipped lines unchanged, the times free, and each similarity to its first three decimals. The tiering prototype's trail is compared the same way, with each spend by its leading digits too, since releasing the unspent reservation leaves floating-point remainders such as 0.0010000000000000009.
