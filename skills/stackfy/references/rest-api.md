# REST API

## Concept

A REST API maps HTTP methods and paths to operations on a resource. Creating answers 201 with the new resource, listing answers 200 and filters through query parameters, an action on a sub-path answers 200 with the result, and removing answers 204 without a body. Input is parsed and validated where it enters, and every failure becomes a status code with a JSON body that explains it: 400 for invalid input, 404 for an unknown resource or route, and 500 for anything unexpected. A file arrives as a multipart form, whose parts each carry a field name, and a file part also a file name and a media type.

## How the course implements it

The Grafana MCP lesson of module 1 serves a **Fastify** 5 app whose routes exist to produce telemetry ([telemetry](telemetry.md)). GET /health answers {"message":"ok"}. GET /students/db-leaky-connections answers 200 with the students, the rows of the seeded table as **PostgreSQL** returns them, and Students retrieved successfully as the message, until its two pooled connections are leaked ([sql-database](sql-database.md)), and from then on answers 500 with the error Internal Server Error and the message Failed to retrieve students data after a one-second wait. POST /students/db-leaky-connections/reset answers 200 with Leaked connections cleaned up, cleanedCount, and remainingConnections, and leaves the next request free to succeed. Any other route gets **Fastify**'s own 404 body, Route GET:/students not found included, although the README lists GET /students. The entry point listens on PORT, 9000 by default, on every interface, and prints Server is running on, the address **Fastify** reports, and the port in parentheses, after **Fastify**'s own JSON log lines.

The smart model router gateway of module 2 serves one route, POST /chat, with **Fastify** 5, whose JSON Schema requires an object with a question of at least 5 characters, and answers 200 with the model that answered and its content as JSON ([model-routing](model-routing.md)). Every failure is **Fastify**'s own JSON error, with statusCode, code, error, and message: 400 with **Ajv**'s message when the body is missing, is not an object, lacks the question, or has a shorter one, 400 when a JSON body is empty or does not parse, 415 for a content type other than JSON or plain text, and 404 with Route GET:/chat not found, the method and the URL, for any other route. When the model call fails, the handler prints Error handling /chat request: and the error to standard error and sets status 500 without sending it, so the request never gets an answer. The entry point listens on port 3000 of every interface and prints server running at 3000, and the module's tests inject their requests into the app without listening.

The LangChain intro of module 2 serves its graph ([state-graph](state-graph.md)) the same way: **Fastify** 5 on POST /chat, the same schema, the same error bodies, the same unanswered 500, and the same entry point and tests. It answers 200 with the graph's output as plain text.

The medical appointment lesson of module 2 serves its graph ([state-graph](state-graph.md)) with **Fastify** 5 on POST /chat, whose JSON Schema requires a question of at least 10 characters, with the same error bodies as the gateway. It answers 200 with the graph's final state as JSON, and when the run throws, it prints ❌ Error processing request: and the error to standard error and answers 500 with the error An error occurred while processing your request. The entry point listens on port 3000 of every interface and prints Server is running on http://0.0.0.0:3000, and the module's tests inject a scheduling question and a cancelling one, naming the professionals the appointment service lists, without listening. In the final version, the scheduling test is skipped, and the other books the appointment before cancelling it and expects the intent cancel and the action's success in the answer.

The RAG lesson of module 2 over students serves one route, POST /sales, with **Fastify** 5, whose JSON Schema requires an object with a question of at least 3 characters, with the same error bodies as the gateway. It runs its graph on the question ([text-to-query](text-to-query.md)) and answers 200 with the answer, or No answer generated without one, the follow-up questions, or an empty list, and the query and the error only when the graph set them. Before the run, the handler prints an empty line, a rule of 60 ═, 📊 Sales Analytics: with the question in quotes, and another rule. After it, it prints an empty line, a rule, ✅ Analysis completed in with the milliseconds and ms, 💬 Answer: with the answer's first 100 characters, followed by ... when it is longer, ❓ Follow-ups: with their count and suggested, a rule, and an empty line. The entry point listens on port 4000 of every interface, prints Server is running on http://0.0.0.0:4000, sends the route the question Which courses are commonly bought together? through **Fastify**'s in-process inject, prints the answer, and keeps serving. In the template, every question gets No answer generated with no follow-up questions, and a blank question also gets the error No valid question found in messages. The document analysis lesson of module 2 serves one route, POST /chat, with **Fastify** 5 and **@fastify/multipart** 9, which takes a PDF and a question as a multipart form, up to 10 MB per file. It runs its graph on them ([state-graph](state-graph.md)) and answers 200 with the file's name, the question as it came, and the text of the graph's last message, or No answer generated when that text is empty. It then prints 🧪 Testing with default document..., sends the route the PDF in its docs folder, file first, with the question describe what's on this document through **Fastify**'s in-process inject, prints 📝 AI Response: with the answer and a blank line, and keeps serving. notas-api serves tasks with node:http and no framework, by design. ## What usually goes wrong in other languages

- notas-api, the smart model router gateway, the LangChain intro, the medical appointment lesson, and the Google Trends agent always listen on port 3000, and the RAG lesson over students and the document analysis lesson on port 4000, while OpsPilot, cfp-platform's api, the Grafana MCP lesson's app, and the legacy customers API read PORT. The cases start them with PORT, so a transcription reads it, falls back to 3000, or 4000 for the lessons on port 4000 and 9999 for the legacy customers API, and prints the port it listens on, except in the startup lines of the lessons on port 4000, which always name 4000 and where the cases accept any port. The multiple MCP tools lesson keeps port 3000 fixed and sends its only request itself, so its cases need that port free.
- The gateway and the Grafana MCP lesson's app answer **Fastify**'s error bodies, so a transcription answers the same JSON with statusCode, error, and a message. Only the unknown route's message has to match, because the validation messages come from **Ajv**, and every validator words them differently.
- **Fastify** parses only JSON and plain text, so a form body or a body without a content type answers 415, while a request with neither a body nor a content type fails validation. Its schema counts code points, neither bytes nor the UTF-16 units that **Java**, **C#**, and **JavaScript** strings count, so ação and 🙂🙂🙂 are too short. It also coerces scalars, so a question of 12345 passes as text. Transcriptions accept only strings, and no case sends anything else.
- When the model call fails, the gateway never answers. Transcriptions answer 500 with an empty body, which is what its handler means, and no case checks it.
- The legacy customers API serializes every answer through its response schema, which keeps only the properties it names, so GET by id leaves out fields such as an email, its 404 answers {} instead of the handler's error, and PUT's validation failure keeps only the message. Serializers in other frameworks write the whole object, so a transcription builds each body with exactly those fields. POST declares no 400 schema and answers **Fastify**'s whole error body.
- Deleting a well-formed id that matches nothing never answers, because the legacy API's handler sets 404 without sending it. Transcriptions answer 404 with an empty body, which is what the handler means, and no case checks it.
- The multiple MCP tools lesson and the LangChain intro answer their text as text/plain. **FastAPI** encodes a returned string as JSON, quotes included, so a transcription returns a plain-text response, and the cases compare the printed body.
- That lesson's entry point prints its startup line before reading the CSV, and exits once the body is printed or the CSV is missing (exit code 1), although its server still listens. A transcription may send the request through its framework's test client or to its own port, and a server thread must not keep the process alive, as a **Python** thread that is not a daemon would.
- The entry points of the Google Trends agent, the RAG lesson over students, and the document analysis lesson keep serving after they print their own answer, so their cases wait for that answer before sending theirs. A transcription of the Google Trends agent sends its question only once it listens and keeps both running.
- The RAG lesson over students leaves the query and the error out of its answer when the graph never set them, as JSON.stringify drops undefined, so a transcription omits them instead of writing null, and its log prints undefined after 💬 Answer: when there is no answer, where **Python** would print None.
- The document analysis lesson's test reads docs/a-comprehensive-overview-of-large-language-models.pdf beside the source, so a transcription keeps that folder, and the cases check that the whole file reaches the model.
- **@fastify/multipart**'s request.file() hands over the first file as soon as its part begins, with only the fields read so far, and reads no further until the file is consumed. A question after a small file still arrives in the same chunk, but after a file larger than a stream buffer it is never seen, so the README's curl, which sends the file first, answers 400 with a real PDF, while the in-process test, which also sends the file first, works. Frameworks that read the whole form first, such as **FastAPI**, **Flask**, or **Go**'s ParseMultipartForm, accept either order, which is what the handler means, and no case sends a large file before the question.
- Only the first file counts, whatever its field name, and only its declared media type, which **busboy** lowercases and strips of parameters, so a text file declared as application/pdf reaches the model and a PDF sent as application/octet-stream is rejected. A framework that reports the raw header, such as **FastAPI**'s content_type, needs the same normalization.
- A body that is not multipart fails inside the handler, so it answers 500 with the plugin's message, the request is not multipart, which the cases check as any non-empty text. **FastAPI** answers 422 when its form parameters cannot be read, so a transcription reads the form itself. A file over 10 MB fails the same way once it is read, and no case sends one.
- The startup line must reach standard output before the runner stops the server with SIGTERM. **Python** buffers output to a pipe and loses it on that signal, so it flushes the line.
- An empty body counts as an empty object, so a missing body is a validation failure, not invalid JSON. **Python**'s json module rejects an empty string, so the transcription checks for it first.
- An empty status filter is invalid, not all. **Python**'s query parser drops blank values unless asked to keep them, which would turn the filter into all.
- Unknown methods on a known path, such as PUT /tasks, answer 404 with Route not found. **Python**'s http.server answers 501 with an HTML page for any method without a handler, and routers such as those of **Flask**, **FastAPI**, and **Go**'s standard library answer 405, so every method goes through the same router.
- **Python**'s http.server logs every request to standard error, which the original never does.
- The body is parsed whatever its content type. **Express**, **Flask**, and **FastAPI** parse JSON only when the request says it is JSON and answer their own error bodies, so a framework needs both behaviors set to match.
- Unknown fields in the body are dropped, so sending a status never changes that a task is born open, and a padded title is stored trimmed.
- A 204 carries no body and no content type.
- OpsPilot compares its trace exactly, so events carry tool and toolArgs only for actions and round, approved, and timestampMs only for critiques. A transcription leaves absent fields out instead of writing them as null.
- The reflect flag must be a real boolean. **pydantic** in its default lax mode turns strings such as true or yes into booleans, so the field is strict.
- **zod**'s issues are its own, so the cases check validation failures by their error code and a non-empty list of issues, except the Invalid JSON issue, which the module writes itself.
- From unit 6, the X-Request-Id header repeats the body's requestId, which the cases compare. A body that does not parse fails before the route, so its answer has no X-Request-Id, and GET /requests and GET /stats never send one.
- Framework CORS middlewares, such as **Starlette**'s, answer a preflight from an origin they refuse with 400 instead of 204, so a transcription writes the middleware itself.
- cfp-platform's api answers 201 to every creation, as **NestJS** does for any POST, while **FastAPI** answers 200 unless the route names another status.
- Its 404 body names the method and the path for unknown paths and for known paths with another method, where **FastAPI**, **Flask**, and **Go**'s standard library answer 405 or a body of their own, so every method goes through one handler for unknown routes.
- A form body's fields arrive as text, so isGDE=true fails as not a boolean, and a body of another type leaves every field missing. **FastAPI** answers 422 to both unless the route reads the raw body.
- Malformed JSON answers 400 with the parser's own message, which every language words differently, so the cases check only that the message is text.
- The ids are short random strings of lowercase letters and digits, and the cases check that shape, so a UUID fails.
- **Express** 5 leaves the body undefined when no parser takes it, so brag-bot's route fails reading the definition of a form, a plain text, or a missing body and answers 500, where **Express** 4 would have given an empty object and a 400. Only a JSON object without a truthy definition answers 400, so a definition of spaces goes on to the model, and a number or a list fails in the flow with the 500.
- brag-bot's ids are UUID version 4, which the cases check by that shape.
