# Browser built-in AI

## Concept

A browser can ship a language model and expose it to pages through a JavaScript API, so the page prompts it on the user's device with no server, API key, or network once the model is downloaded. **Google Chrome**'s built-in AI runs **Gemini Nano** behind the Prompt API. The page asks whether the model is available, still to be downloaded, downloading, or unable to run on the device, and can start the download with a monitor that reports its progress. It reads the model's sampling parameters and creates a session with a system prompt, the languages it expects, and the temperature and top-k to sample with: a lower temperature favors the likeliest words, and top-k leaves only the k likeliest to choose from. Then it prompts the session and either waits for the whole answer or streams it in text chunks, which an abort signal stops midway, and the session keeps the conversation for later prompts. A session created for several modalities also takes images and audio, as typed parts of a message beside its text. The browser ships smaller task models behind their own APIs too, checked, downloaded, and created the same way: a translator for one pair of languages and a language detector that ranks the languages a text is likely in. What the page asks these models and what it shows are the program's boundary.

## How the course implements it

The first Web AI example is a single HTML page with no package and no build, which any static server delivers. It loads **markdown-js** 0.5.0 (the `markdown` package) from **jsDelivr** as a classic script, and an inline script asks the built-in model one question as soon as the page loads. It reads the model's parameters and logs them, shows Gerando resposta..., and creates a session with Portuguese as the expected input language, the default temperature and top-k from those parameters, and a system prompt asking for clear and objective answers. Then it streams the answer to Quem inventou o JavaScript?, sent as a user message, clears the output, appends each chunk to the text received so far, and renders that whole text as Markdown into the output element after every chunk.

The second Web AI example turns the page into a form, served by **http-server** with no build, whose module script lets the user choose the temperature and top-k for each question. It checks the browser first. Outside **Google Chrome**, without the Prompt API, or when the model cannot run on the device or is still downloading, it explains why in the output and disables Enviar. When the model is downloadable, it downloads it with a monitor that logs the progress to the console, prompts it once with Olá, destroys that session, and checks again. Then it sets a temperature slider from 0 to the maximum and a top-k field from 1 to the maximum, both starting at the model's defaults and showing their values as they change. Each question creates a new session with the form's temperature and top-k, Portuguese as the expected input language, and a system prompt asking for clear and objective answers in plain text instead of Markdown, and streams the answer with an abort signal. The output shows Processing your question... and then each chunk appended as plain text, while Enviar turns into Parar, which aborts the stream and keeps the text received so far.

The third Web AI example keeps the second's form, splits its module script into a view, a controller, and two services, and lets the user attach an image or an English audio file. It also needs the Translator and Language Detector APIs, so its checks list each missing API with the flag that enables it, and it checks the model for English and downloads it with Hello. Before reading the parameters, it creates an English to Portuguese translator, logging its download progress, and a language detector, and when either fails the output says the translation APIs could not start and Enviar is disabled. Each question destroys the previous session and creates one that expects English text, audio, and images and answers in English text, with the system prompt in English as a typed text part. The message holds the question as a text part, followed by the attached file as an image or audio part whose value is a Blob of the file's bytes and type, and the file stays attached to later questions until removed. The answer streams as plain text, as in the second example. Then the output shows Traduzindo resposta... while the detector ranks the languages of the whole answer and the translator streams it into Portuguese, and the translation replaces the answer unless the detector ranks Portuguese first. Parar aborts the stream, which errors, so the output shows the error in place of the text received so far and nothing is translated.

The pages around the models follow [browser-app](browser-app.md).

## What usually goes wrong in other languages

- The Prompt, Translator, and Language Detector APIs exist only in **Google Chrome**'s JavaScript, so a target that runs in the page reaches the same LanguageModel, Translator, and LanguageDetector globals through its bridge to JavaScript, and a target outside the browser has no equivalent, as the table below says. The closest idea outside the browser is a model served locally, as [llm-http-api](llm-http-api.md) does with **Ollama**, which teaches something else.
- The API changed after the lessons. **Google Chrome** 152 exposes LanguageModel to pages without a flag, but pages no longer get the parameters, the numeric temperature and top-k are left to Chrome Extensions while pages get descriptive sampling modes in an origin trial, and expected languages are declared as expected inputs, where Portuguese is not listed yet. The second and third examples still check availability with a list of languages, which Chrome ignores, and the third treats a translator availability of no as missing, a value Chrome replaced with unavailable, so an unsupported pair only fails when the translator is created. A transcription keeps the lessons' calls, which the cases check, and points out the change.
- The model needs a download of several gigabytes and hardware that meets Chrome's requirements, and a fresh headless profile reports it unavailable for Portuguese inputs and downloadable otherwise, reports the translator and the detector downloadable as well, and refuses to create any of them without a user gesture. The first page stops with `LanguageModel.params is not a function`, and the second and third show the refusal. The cases therefore replace the three globals with stand-ins, through a script that runs before the page's own, which record every call, answer each availability check with the state the case needs, report download progress to the monitor, answer the parameters with Chrome's documented defaults (temperature 1 of at most 2, top-k 3 of at most 128), stream a recorded answer and translation, and rank the answer's languages as the case needs.
- Streamed chunks are deltas in current **Google Chrome**, while early versions sent the whole text so far, which is why the pages append the model's chunks. The stream comes back at once instead of as a promise, so awaiting it changes nothing in **JavaScript** but fails from **Python**, whose bridge only awaits promises. **Pyodide** iterates the stream with async for, while other bridges read it through its reader. A bridge also has to hand the session options and messages over as plain JavaScript objects, which **PyScript** does with its to_js.
- From WebAssembly, every promise turns into callbacks. **Go** awaits one by passing its then method two functions that feed a channel. Only a goroutine may wait on that channel, since a callback that blocks freezes the page, which is why the submit handler starts one for each question.
- The translator also streams deltas, one per sentence, each after the first starting with a space. The third page keeps only the last chunk, as if each held the whole translation so far, so a longer answer ends up as its last sentence translated. The cases translate one-sentence answers, where both readings agree, so a transcription may append the translator's chunks. The detector's ranking comes as a list from most to least likely, and the page compares only the first language with pt.
- The attached file reaches the model as a Blob with the file's type, which the input's File already is. A bridge hands that JavaScript object over as it is, since copying its bytes into the target and back gains nothing, and the cases compare the Blob's type and size.
- Aborting the signal handed to promptStreaming errors the stream with the signal's reason, an AbortError. The second page leaves it uncaught, keeping the text received so far, and also aborts its controller once an answer ends, which changes nothing. The third catches it and shows Erro: signal is aborted without reason in place of the answer. A transcription that only stops reading leaves the model generating, and the cases expect the abort.
- The second page creates a new session for every question with the form's current values, so nothing carries over between questions. It means to destroy the previous session first but never keeps it, so a transcription may destroy it, and its cases leave that out. The third keeps the session and destroys it before creating the next, which its cases expect. The form's values arrive as text, parsed as a decimal temperature and an integer top-k, and the system prompt is an indented template literal, so the cases compare prompts with whitespace collapsed.
- The second and third pages write Processing your question... and clear it before the browser paints, so nobody sees it. The cases still expect it before the answer, and a transcription may keep it until the first chunk arrives. The download progress of the model and the translator only reaches the console, as whole percentages, which the cases read too.
- The first page renders the whole text again after every chunk, so unfinished Markdown, such as bold still open, shows its asterisks until the closing ones arrive. **markdown-js**, **marked**, **markdown-it**, and **Python-Markdown** show the same text at every step of this answer, so any renderer that leaves unclosed emphasis as it is passes the cases.
- The rendered Markdown goes into the page as HTML. Frameworks escape text by default, so a transcription inserts it as HTML (in **React**, through dangerouslySetInnerHTML), or the tags show literally. The first page does not sanitize the model's output, and sanitizing it changes nothing the cases see. The second and third pages show plain text instead, so rendering their answers as Markdown or HTML changes what they show.
- **markdown-js** is a global from a classic script, not a module, so a bundled transcription imports the `markdown` package or another renderer instead.

## How close common targets get

Only the code that prompts the models and shows their answers moves.

| Target                                          | Fit                | Library                                                                                                                                              |
| ----------------------------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **JavaScript** and **TypeScript**               | Direct equivalent  | The LanguageModel, Translator, and LanguageDetector globals, typed in **TypeScript** by `@types/dom-chromium-ai`, with **markdown-js** or **marked** |
| **React**, **Vue**, **Angular**, and **Svelte** | Direct equivalent  | The same globals called from a component, with **marked** rendering into an element that takes HTML                                                  |
| **Python**                                      | Substitute         | **PyScript** calling the globals through its window object, with **Python-Markdown**                                                                 |
| **Rust**                                        | Substitute         | **Leptos** compiled to WebAssembly, with hand-written wasm-bindgen bindings to the globals and **pulldown-cmark**                                    |
| **C#**                                          | Substitute         | **Blazor** WebAssembly calling the globals through JavaScript interop, with **Markdig**                                                              |
| **Go**                                          | Substitute         | **Go** compiled to WebAssembly calling the globals through syscall/js, with **goldmark**                                                             |
| **Java**                                        | Nothing comparable | The page stays in **JavaScript** and is explained instead of transcribed                                                                             |
| **C++**                                         | Nothing comparable | The page stays in **JavaScript** and is explained instead of transcribed                                                                             |

Tested transcriptions exist for **Python** (the first example) and **Go** (the second).

## Tolerance

A real model's answer, translation, and language ranking change with every run, device, and **Google Chrome** version, so the cases never depend on one. The stand-in streams the same chunks every time, 30 ms apart so each renders on its own, and holds the stream after five chunks when a case stops it with Parar, so the answer always stops at the same text. The cases compare the calls, with attached files by type and size, every text the output and the button show with whitespace collapsed, and the words that end up bold exactly.
