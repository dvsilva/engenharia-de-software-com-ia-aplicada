# Component framework

## Concept

A component framework builds a page from components. Each component owns a template, its state, and its styles, receives data from its parent through inputs, reports what happened through outputs, and renders again whenever its state changes. Templates bind state into text, properties, classes, and event handlers, branch and repeat with control flow, and format values on the way out, such as a currency or a date. Form fields bind to state in both directions, or belong to a form model whose validators decide whether the form may be sent and which message each field shows. Components ask the framework for shared services, such as an HTTP client, and show what is loading, what failed, and what arrived. A client-side router maps the address to a component, loads it lazily, and changes the address without reloading the page, so the server answers every path with the same page. Each component's styles stay inside it, while a global stylesheet holds the design tokens: custom properties with semantic names for colors, fonts, and a spacing scale, redefined when the system prefers a dark color scheme. A server can also render the first response from the same components, so the page shows its content before any script runs, and the browser then hydrates that HTML, attaching state and listeners to the elements it already has instead of building them again. Until hydration ends, the page shows but does not react. What the page shows and how it reacts are the program's boundary, so the same application can be written in any component framework.

## How the course implements it

The first UI/UX lesson builds pix-app with **Angular** 21 standalone components, using AI tools for the design: a briefing turned into design tokens, a **Figma** frame and its specs turned into the statement, a **Google Stitch** export refactored into the receipt, and an accessibility prompt for the error modal ([coding-agent-harness](coding-agent-harness.md)). The **Angular CLI** builds it and serves it in development with ng serve.

The global stylesheet declares the tokens on :root: primary #0A192F, action #64FFDA, error #FF6B6B, background #F8F9FA, text #0A192F, headings in Montserrat, body text in Inter, and spacings of 8, 16, 24, and 32 px. Under prefers-color-scheme dark, the background becomes #112240 and the text #F8F9FA. Components take their colors and most spacings from these tokens through var(), apart from a few rgba values the receipt derives from them.

The root component lays a side menu, with router links to Pix (/pix) and Extrato (/extrato), beside a main area holding the router outlet, and its :host style makes the two sit side by side at full height. The router redirects the empty path to /pix and loads each page lazily.

The transfer page keeps the Pix key, the amount, the scheduling date, whether the error modal shows, and the receipt's data in signals. A template-driven form binds the three fields with ngModel, and submitting it takes the amount, or zero when the field is empty, and either opens the error modal when it is above 5000 or stores the key and the amount as the receipt's data. An @if block then shows the receipt in place of the form, passing the recipient and the amount through input signals, and another shows the error modal, whose close output hides it. The scheduling date is never used. The receipt formats the amount with the currency pipe in BRL and shows a fixed date, time, institution, and transaction id, plus share, download, print, home, and new transfer buttons without handlers. The statement holds three fixed transactions in a signal and repeats them with @for tracked by id, choosing the arrow icon and the received or sent classes by direction, and formatting dates with the date pipe as dd/MM/yyyy HH:mm and amounts with the currency pipe. The error modal's accessibility follows [web-accessibility](web-accessibility.md). Icons are Material Symbols ligatures loaded from **Google Fonts**.

The third UI/UX lesson's cfp-platform puts an **Angular** 21 frontend beside its api in an **Nx** workspace ([full-stack-monorepo](full-stack-monorepo.md)). Its global stylesheet is empty, and each page repeats the same glassmorphism styles with hard-coded colors and gradients. The root component holds a menu above the router outlet, whose links to Cadastro de Evento (/event/new), Cadastro de Palestra (/talks/new), and Dashboard (/dashboard) take the active class on their own route. The router loads each page lazily and redirects the empty path to the dashboard, and the configuration provides the router and the HTTP client, which each page asks for with inject() and calls through a subscription with next and error handlers.

The event page builds a reactive form with FormBuilder's nonNullable group: nome, endereco, and data are required, and capacidade starts at 0, is required, and must be at least 1. A field's message shows only while it is invalid and touched, and submitting an invalid form marks every field touched and sends nothing. A valid form posts its raw value to /api/events, capacidade as a number, while a status signal moves to loading, which disables the button and makes it read Cadastrando..., and then to success, which shows its message and resets the form to its initial values, untouched, or to error, which shows the error body's message or a fallback. The proposal page binds its four fields to signals with ngModel and never validates, so submitting always posts name, email, talkTitle, and isGDE to /api/speakers, with the same states, its fields disabled while loading, and the signals cleared after success. The dashboard fetches /api/speakers in ngOnInit and shows, through one @if chain, a loading status, an error alert with Retry, an invitation to submit the first talk when the list is empty, or a table of the speakers tracked by id, each with a GDE or a Speaker badge. The accessibility of the forms and of these states follows [web-accessibility](web-accessibility.md).

The fifth UI/UX lesson's brag-bot is an **Angular** 21 application rendered on the server by @angular/ssr, in an **Express** server that also serves its API ([rest-api](rest-api.md)). Every path renders on the server, and the browser hydrates the page with event replay, which records the events that arrive before hydration and plays them back afterwards. The application runs without zone.js, and its styles are **Tailwind CSS** 4 utility classes, compiled through **PostCSS**, over a dark slate main area. The router loads two pages lazily: the dashboard at the empty path and a brag's details at detail/:id. A service provided in root keeps the brags and a loading flag in signals, so the list outlives the route but lives only in the browser's memory. The dashboard binds a textarea, labeled Descreva sua conquista de forma informal, to a plain property with ngModel, and its submit button, Destilar Conquista, stays disabled while the trimmed draft is empty or a brag is loading. Submitting hands the draft to the service and clears the field at once. The service sets the loading flag, which turns the button into a spinner with Destilando..., posts the draft to /api/brag with the HTTP client over fetch, and on success puts the new brag first, mapped from the answer: businessImpact becomes impact, the metrics are joined with a comma and a space, technologiesUsed becomes technologies, and a missing id becomes a random UUID. On failure it only logs the error and clears the flag, so the draft is lost. The list repeats a card per brag with @for tracked by id, each a router link to its details holding the title, the context, and a badge per technology, and @empty shows Nenhum Brag Document gerado ainda. with an invitation to describe the first success. The details page always links back with Voltar ao Dashboard. It reads the id once from the route's snapshot, computes the brag from the service, and shows its title, its technologies, and three sections, O Contexto, O Impacto, and Métricas e Resultados, never the action taken, or else Conquista não encontrada with a link, Retornar, to the dashboard. The server renders each request with a fresh service, so it renders the dashboard empty and every details address as not found, and so does the browser when a details address is opened directly. The root component's spec expects the generated Hello, brag-bot heading, which the root does not render, so ng test fails, and a transcription does not need to port it.

The Context7 lesson of module 1 holds nextjs-better-auth-demo, which an assistant generated from the lesson's prompt ([coding-agent-harness](coding-agent-harness.md)): a **Next.js** 16 application on the App Router with **React** 19 and **TypeScript**, styled with **Tailwind CSS** 4 utility classes. Folders under app are routes: app/page.tsx answers /, app/login/page.tsx answers /login, and app/api/auth/[...all]/route.ts handles every path under /api/auth on the server ([user-authentication](user-authentication.md)). The root layout keeps create-next-app's title, Create Next App, and the language en, and loads the Geist fonts through next/font/google. Both pages are client components, marked "use client", that center a white card over a dark gradient. The home page reads the session with the auth client's useSession hook and shows Carregando... while it is pending, then Hello World with either Logado como and the user's email, or name when there is no email, and a Sair button that signs out and refreshes the router, or Você não está logado and a plain link, Ir para Login, to /login. The login page shows Bem-vindo, Faça login para continuar, and one Entrar com GitHub button with **GitHub**'s mark as an inline SVG, which starts the sign-in with / as the address to return to.

OpsPilot's unit 8 adds the War Room, a single page in **React** 19 and **TypeScript** that **Vite** 8 serves and builds under a base path ([browser-app](browser-app.md)), with no router. The root component keeps its state in useState: the API's address, read from storage once, whether the settings are open, the turns, the conversation id, the approval flag, whether a request is out, the held request, the turn whose reasoning is open, and the last message that failed, plus the request's AbortController in a ref. Its children, SettingsGear, ChatThread, ApprovalCard, Composer, TraceDrawer, and EmptyState, report through callback props. The composer binds a textarea, labeled Mensagem, and the Exigir aprovação checkbox, sends the trimmed text when it is not blank, through Enviar or Enter without Shift, and clears the field. While a request is out, Enviar becomes a disabled Enviando…, both fields are disabled, and Cancelar appears, which aborts a chat request. Sending appends the user's turn, labeled Você, at once, dropping any error turn, and posts to the API ([rest-api](rest-api.md)) through a client that parses every answer with **zod** ([schema-validation](schema-validation.md)). A 200 appends the assistant's turn, labeled OpsPilot, with the answer as plain text and Ver raciocínio when the trace has events, and keeps its conversation id for the next message. A 202 shows the held request's card ([agent-observability](agent-observability.md)), an aborted request leaves only the user's turn, and any failure appends a turn labeled Sistema with an Erro banner, the failure's message, and Tentar de novo, which sends the same message again as a new turn. The card shows Ação pendente and the summary, blocks the composer while the request is held, and sends Aprovar or Negar as the decision with both buttons disabled while it is out, then shows Aprovado, Negado, or Erro na decisão with the failure's message, and appends the answer of an approval or a denial as the assistant's turn. Ver raciocínio opens a drawer listing each trace event's type and content, nó: and its node, and tool: and its tool when there is one. The gear opens the settings, whose draft resets to the current address each time they open, and saves an http or https address, trimmed and without trailing slashes, to localStorage. tokens.css holds the design tokens, with IBM Plex Sans from **Google Fonts**, and the components share one stylesheet of BEM classes. The module's own tests run in **Vitest** with **Testing Library** over jsdom.

## What usually goes wrong in other languages

- Importing FormsModule or ReactiveFormsModule adds novalidate to every form, so the required attributes never block a submit: pix-app shows a receipt of R$0.00 to an empty recipient, and cfp-platform's proposal page sends empty fields. ngSubmit also prevents the page from reloading. A transcription adds novalidate (noValidate in **React**) and prevents the submit's default action itself, or the browser blocks the submit or reloads the page.
- ngModel on a number field holds a number, or null when the field is empty, which the submit turns into zero. A transcription parses the field's text the same way instead of keeping it as a string. The limit is strictly above 5000, so 5000 shows the receipt and 5000.01 the modal.
- The pipes format with **Angular**'s default locale, en-US, whatever the browser's language, so amounts read R$1,234.50, not R$ 1.234,50. A transcription fixes en-US in Intl.NumberFormat with the BRL currency. The date pipe converts the stored UTC time to the browser's time zone, and no Intl locale produces dd/MM/yyyy HH:mm exactly (en-GB adds a comma), so a transcription builds it from the date's local getters.
- **Angular** emulates style encapsulation, so element selectors in a component's stylesheet, such as the transfer page's section, h2, label, input, and button, and the root's aside and main, reach only that component's own elements, never those of the receipt or the modal it renders. Plain global CSS lets the transfer page's button rule give the modal's close button and the receipt's buttons a top margin, and **CSS Modules** do not help, since they rename classes but leave element selectors global. The cases read those margins. In **React**, each stylesheet with element selectors goes inside a CSS @scope block keyed to the component's root class, with :host becoming :scope, and the root's block stops at the routed content with `to (main > *)`. This keeps the class names the cases read, which **CSS Modules** would rename. Stylesheets that only use the component's own class names need no scope.
- cfp-platform's pages share class names with different values, such as the dashboard's 900px card against the forms' 500px. A stylesheet that a lazy **React** page imports stays in the document after the page leaves, so with plain global CSS the last one loaded wins, and the cases read the dashboard's card after a visit to the event page. Each page's root gets a class of its own for its @scope block, and the root's own rule becomes :scope, because selectors inside @scope match only below the root.
- **Angular** wraps each component in a host element (app-root, app-pix-transfer, app-error-modal) that **React**, **Vue** fragments, and **Svelte** do not render, so the cases never select host elements, and a transcription gives the root's layout to a wrapper element of its own.
- The empty path redirects with history replaced. The cases also open /extrato directly, so the server answers every path with index.html, as ng serve and **Vite**'s dev server do.
- pix-app's transfer page keeps its state in its component, so leaving through the menu and coming back shows an empty form again. A transcription keeps that state in the page component, not in a store that outlives the route.
- The Escape listener on the document exists only while the modal does, because **Angular** removes host listeners with the component. In **React**, an effect adds it and its cleanup removes it.
- Each icon is its ligature name as text, which the cases read. A transcription keeps the Material Symbols font and those names, since icon components that draw SVG show no text.
- pix-app's spec files are stale: one expects a heading the root does not render, and another imports a class that does not exist, so ng test fails. The cases replace them, and a transcription does not need to port them.
- Reactive form directives take the disabled binding of cfp-platform's event fields and only warn, so those fields stay enabled while the form is sent, while ngModel does disable the proposal page's fields. The cases read both.
- A field becomes touched when it loses focus or when a submit marks them all, and the cases fill fields without leaving them, so no event message shows before the first submit, and filling a field afterwards hides its message at once. After a success, the reset form shows capacidade as 0 and no messages, while the success message stays until the next submit, even one the validators stop.
- The proposal page shows the error body's message as it arrives. For the api's validation errors it is a list, which **Angular**'s interpolation joins with commas and no spaces. **React** renders a list's items with nothing between them and **Vue** renders it as JSON, so a transcription joins the list itself.
- **Angular**'s HTTP client fails on an error status and parses an error body as JSON when it can, keeping it as text otherwise, so the dev server's empty answer when the api is down has no message, and the page shows its fallback. fetch resolves on any status, so a transcription checks response.ok and parses the body itself.
- The dashboard fetches each time its route activates, and the cases count its requests. **React**'s StrictMode runs effects twice in development, which sends the request twice, so a **React** transcription renders without it.
- The cases read each loading state while the replay holds the answer, so a transcription sets that state before the request starts.
- pix-app's and brag-bot's start scripts fix port 4200, so their cases run `npx ng serve --port $PORT --host 127.0.0.1`, which for brag-bot also renders on the server and mounts server.ts's API, and cfp-platform's run the frontend alone with `npx nx run frontend:serve --excludeTaskDependencies --port=$PORT --host=127.0.0.1`. A **Vite** transcription runs `npx vite --port $PORT --host 127.0.0.1 --strictPort`.
- The runner waits until the command's standard output and error close, so a command that starts a server in the background, as cfp-platform_v1's suite command starts the frontend before **Cypress**, redirects that server's output, such as to /dev/null. Otherwise any of the server's processes that outlives the command keeps them open, and the case waits until it times out.
- The tested **React** transcriptions use **TypeScript** 7, whose package lacks the **JavaScript** API that **Cypress** compiles its specs through, so cfp-platform_v1's suite, which stays as it is, keeps **TypeScript** 5.9 in a project of its own. The original declares **Cypress** ^15.8.0, which now resolves to 15.21.1, so that project pins 15.13.0, the version the original's lock file holds and the cases were recorded with.
- That project leaves the **Nx** workspace, so its **Cypress** configuration drops **Nx**'s preset and @nx/cypress, keeping the project id and a base URL read from BASE_URL. The specs, the support file, and the fixtures already sit where **Cypress**'s defaults look, under cypress, so only the screenshots and videos move, from the workspace's dist folder to cypress, and the project's ignore file lists them. The preset also turns chromeWebSecurity off, which no case needs, since the page calls only its own origin.
- **Next.js** renders client components on the server too, so the login page's button arrives as HTML before **React** hydrates it, and a click before that does nothing. The cases wait until the page is idle before clicking, and a transcription keeps the button's work in the browser or behind a form, either of which works once the page is idle. The home page renders its loading state on the server, so its texts only appear in the browser, and no case reads them while loading.
- nextjs-better-auth-demo's links are plain anchors, not next/link, so going to /login loads a new page. After signing out, the session hook reads the session again and the home page shows the signed-out state, while router.refresh only reloads server components, of which the page has none. A transcription updates the page from the sign-out itself.
- The title and the language stay create-next-app's, Create Next App and en, under Portuguese texts, and the cases read both.
- next dev reads PORT, so the cases run `npx @better-auth/cli migrate --yes && npm run dev`, the README's order. The utility classes and the Geist fonts change no text, and the cases read none of the styles.
- The War Room shows the answer's Markdown as plain text, and the cases read its asterisks and line breaks as the API sent them, so a transcription renders no Markdown.
- The War Room's client turns each failure into its own message: a fetch that fails reads Não foi possível falar com a API, another status Falha no chat (HTTP n) or Falha na aprovação (HTTP n), a 200 without a valid answer or conversation id Resposta sem answer válida, an empty answer Resposta sem answer, and a 202 without its held request Resposta 202 inválida. The cases replay each one.
- Tentar de novo sends the failed message as a new user's turn, so the thread shows it twice, and an error turn disappears only when a message is sent.
- The first message leaves conversationId out of the body, since the API rejects null, and every later one sends the id of the latest answer that carried one, an approved run's included.
- The held request's card stays after its decision, showing Aprovado or Negado, until another held request replaces it, and Exigir aprovação stays checked, so the next message is held again until it is unchecked. While a decision is out, the composer shows Enviando… and a Cancelar that aborts nothing, since only chat requests carry the abort signal, and the cases read both.
- The settings reset their draft in an effect and focus the field in a microtask, so right after opening, the field may still show the previous draft. The cases wait a moment after a dialog opens before reading it.
- JSX drops the line breaks a formatter puts around a button's text, while **Vue** and **Angular** templates condense them into a space, so the War Room's cases trim the texts of labels, buttons, and messages, never the answer itself.
- The War Room's App tests fail on **Node.js** 25 and later, whose own localStorage global stays undefined without --localstorage-file and hides jsdom's, while they pass on **Node.js** 22, which the deploy workflow uses. The cases replace them, and a transcription does not need to port them.
- brag-bot's cases read the server's HTML before any script runs and expect the heading, the field, the disabled button, and the empty list in it, so a build that renders only in the browser fails them.
- brag-bot's server renders the form, so a user can type before hydration, but **Angular** writes the model's empty value into the field when it hydrates, which clears what was typed. The cases type the draft again until the button takes it, so a transcription that keeps early input passes too. **React** can instead leave the early draft in the field while the component's state stays empty, and filling the field again with the same text, as the cases do, changes nothing **React** sees, so the button stays disabled. A **React** dashboard reads the field in an effect that runs once after hydration and adopts any text it holds.
- brag-bot's cases open the details through a card and check that the document never reloaded, so a transcription moves between its pages in the browser, through its router or the History API, and keeps the list in state that outlives the page component.
- The draft is cleared when the form is sent, before the answer, so after a failure the dashboard looks as it did before, with an empty field and the button disabled again.
- The cases read none of brag-bot's styles. A transcription to a component framework keeps the **Tailwind CSS** classes, and one without a framework turns them into a small stylesheet of its own. **Tailwind CSS** compiles through @tailwindcss/vite in every **Vite** build, as **React Router**'s framework mode, **Nuxt**, and **SvelteKit** are, because through **PostCSS** **React Router**'s server build fails to resolve @import "tailwindcss". Only the production build shows it, since the cases run the dev server.
- A **React** transcription of brag-bot makes its **Express** app, which holds the API's route and **React Router**'s request handler, the server build's entry. **React Router** 8 always builds through **Vite**'s environment API, so that entry goes in environments.ssr.build of the **Vite** configuration, not in build.rollupOptions behind isSsrBuild, as **React Router** 7's custom server template has it. The cases run the dev server, which loads the entry from source, so only the production build shows a misplaced entry.

## How close common targets get

| Target                            | Fit                | Library                                                                                                      |
| --------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------ |
| **Angular**                       | Direct equivalent  | The original's standalone components, signals, and router                                                    |
| **React**                         | Direct equivalent  | **React** 19 with **React Router** in data mode, built by **Vite**, with CSS @scope for component styles     |
| **Vue**                           | Direct equivalent  | **Vue** 3 single-file components with **Vue Router**, built by **Vite**, with scoped styles                  |
| **Svelte**                        | Direct equivalent  | **Svelte** 5 runes in a **SvelteKit** single-page application, whose styles are scoped by default            |
| **JavaScript** and **TypeScript** | Substitute         | Functions that render each view into the DOM, the History API for routes, and CSS @scope, without shadow DOM |

| **Rust**                          | Substitute         | **Leptos** compiled to WebAssembly, with signals, components, and leptos_router                              |
| **Go**                            | Substitute         | **go-app** components compiled to WebAssembly                                                                |
| **Python**                        | Substitute         | **PyScript** rendering into the DOM, with routes kept by the History API                                     |
| **Java**                          | Nothing comparable | The page stays in **TypeScript** and is explained instead of transcribed                                     |
| **C++**                           | Nothing comparable | The page stays in **TypeScript** and is explained instead of transcribed                                     |

Custom elements with shadow DOM hide their elements from document queries and break ARIA references across the shadow boundary, so a framework-free transcription renders into the light DOM.

The War Room is already **React**, so a transcription to **Vue**, **Svelte**, or **Angular** reads the building blocks below from the **React** column, and one without a component framework keeps its classes, roles, and labels, which the cases select.

nextjs-better-auth-demo keeps its pages beside the routes that sign users in, so a transcription to **Vue** moves both into **Nuxt**, one to **Svelte** into **SvelteKit**, and one to **Angular** serves the routes from a server of its own. A target without a component framework renders its two pages on the server from the session cookie instead, with the same elements and texts, since no case reads the loading state.

brag-bot renders its pages on the server and serves its API from the same server, so a transcription to **React** moves into **React Router** in framework mode, whose @react-router/express handler serves the pages from the original's **Express** server beside the API's route, and into **Next.js** only when the student asks for it. That server stays a plain JavaScript file started with `node`, as the original's built server is, so the transcription needs no runner such as **tsx** or **cross-env**. One to **Vue** moves into **Nuxt**, and one to **Svelte** into **SvelteKit**, each with a route for the API. A target without a component framework renders the two pages from its own templates and adds a small script that keeps the brags in memory, sends the draft, and moves between the pages with the History API.

## Tolerance

The page is deterministic once the time zone and the color scheme are fixed, so the cases compare texts, attributes, focus, layout, and computed colors exactly, reading token values in lowercase without quotes. Timing varies, since routes load lazily and the dev server builds first, so the cases wait for each state instead of timing it. cfp-platform's pages show only what the api answers, which the replay fixes, and the replay holds some answers for a second and a half so the cases can read the loading states. nextjs-better-auth-demo's pages show only texts and a link or a button that the session decides, so its cases compare them exactly. brag-bot's pages show what the replayed **Gemini** answers hold, so its cases compare the texts exactly and the ids, random UUIDs, by their shape and by matching a card's address with the details page's. The War Room shows only what the replayed API answers, so its cases compare its texts, states, focus, and the bodies it sends exactly, and hold some answers so they can read the sending state.
