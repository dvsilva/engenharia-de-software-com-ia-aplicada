# Chat model

## Concept

A chat model client wraps a provider's chat completion API in an object. It takes a list of messages with roles (system, user, assistant, and tool) and returns the assistant's message, which holds text, tool calls, or both. A framework puts one interface over every provider, binds the tools a model may call ([tool-calling](tool-calling.md)), and offers structured output: the request carries a schema, the model answers with values that fit it, and the client parses them into a typed result. A gateway such as **OpenRouter** speaks the OpenAI-compatible API in front of many providers, so one client reaches any of their models by name or lets the gateway choose one ([model-routing](model-routing.md)), and the raw endpoint underneath is the one [llm-http-api](llm-http-api.md) describes. A provider's own API, such as **Gemini**'s generateContent, carries the same parts under other names, and some frameworks wrap a call in a flow, a function whose input and output schemas the framework checks.

## How the course implements it

Module 1's embeddings lesson configures a model on **OpenRouter** that neither its template nor its final version builds: the model from NLP_MODEL, google/gemma-3-27b-it:free in the template's example environment, the key from OPENROUTER_API_KEY, **OpenRouter**'s address, a temperature of 0.3, two retries, and the referer and title from OPENROUTER_SITE_URL and OPENROUTER_SITE_NAME as headers. Both declare **@langchain/openai** 0.4 without importing it. The RAG lesson that follows builds that ChatOpenAI and calls it once per question, without streaming, through a prompt template piped into the model and a string parser, so each request holds the whole filled template as a single user message ([retrieval-augmented-generation](retrieval-augmented-generation.md)).

The LangChain intro of module 2 calls no model. It uses only **langchain**'s message classes, as the state of its graph ([state-graph](state-graph.md)): a HumanMessage with the question and an AIMessage with the answer. **LangChain4j** names them UserMessage and AiMessage, which the tested **Java** transcription uses.

The medical appointment lesson of module 2 reaches **OpenRouter** through one service with **@langchain/openai** 1.2 and **langchain** 1.2: a single ChatOpenAI for arcee-ai/trinity-large-preview:free, its only model, at temperature 0.7, with the model list and a provider sort by throughput ([model-routing](model-routing.md)) in every request, and the title IA Devs - Prompt Chaining Article Generator with an empty referer as headers. The key comes from OPENROUTER_API_KEY, and a missing key only prints Assertion failed: OPENROUTER_API_KEY is not set in environment variables to standard error. Every call builds an agent with **langchain**'s createAgent, without tools, that asks for the provider's native structured output through providerStrategy, from a system prompt and a user prompt that are each a JSON object written as compact text. The intent prompt holds the professionals with their ids, names, and specialties, the current date in ISO format, the rules and required fields of each intent, extraction instructions, and three examples, and its user prompt holds the question and five instructions. The message prompt describes a friendly receptionist and five scenarios, and its user prompt holds the scenario, the details, six instructions, and an example message in Portuguese for each scenario. The agent checks the answer against the JSON Schema and returns no structured response when it does not fit, without failing. The service returns success with that response, and when the call throws, it prints Error OpenRouterService and the error to standard error and still returns success, with the error's message instead of data, so the graph's nodes fail on their own ([state-graph](state-graph.md)). The template uses only **langchain**'s message classes: the route wraps the question in a HumanMessage, and the message node appends an AIMessage only when it fails. Its configuration, with upstage/solar-pro-3:free as its only model, and its prompts, which declare a **zod** schema for each answer ([schema-validation](schema-validation.md)), are never loaded, so the template prints nothing about a missing key.

The song highlights lesson of module 2 keeps that service with the same headers, temperature, and provider sort, with arcee-ai/trinity-large-preview:free as the final version's only model and upstage/solar-pro-3:free as the template's. Its structured call builds the same agent, but when the call throws, it prints 🔴 LLM Error: and the error to standard error and returns failure with the error's message, and an answer that does not fit the schema returns success without data, which the nodes report as undefined ([state-graph](state-graph.md)). The template builds the service, and so loads the configuration with its key check, whenever it builds the graph, but no node calls it, and its structured call takes the user prompt before the system prompt, the reverse of the final version. The terminal chat wraps every line in a HumanMessage ([command-line-interface](command-line-interface.md)). The prompts are JSON objects written as compact text and declare schemas for a chat answer and a conversation summary ([schema-validation](schema-validation.md)), which the final version's chat and summarize nodes ask for and the template never does. The chat prompt holds the assistant's role, five tasks, the stored preferences or Nenhuma, four extraction rules, and six examples, and its user prompt the conversation so far or Primeira mensagem, the current message, and four instructions. The summary prompt holds the fields to extract and five rules, and its user prompt the conversation as one role: content line per message, the previous summary or Nenhum, and two instructions.

The safeguard lesson of module 2 keeps a service of the same shape, titled IA Devs - Guardrails with an empty referer, at temperature 0.7 with at most 1000 tokens, and with the model list and a provider sort by price in every request ([model-routing](model-routing.md)). It builds a ChatOpenAI for qwen/qwen-2.5-7b-instruct, and its generate method runs **langchain**'s createAgent, built on its first call, on a system prompt and the user's message and returns the text of the agent's last message. The key comes from OPENROUTER_API_KEY and is never checked. The template builds that model whenever it builds the graph and never calls it, so it runs without a key. The final version builds a second ChatOpenAI the same way for openai/gpt-oss-safeguard-20b and invokes it with one user message to judge the input ([prompt-injection-defense](prompt-injection-defense.md)), and gives the agent the tools of the filesystem MCP server ([model-context-protocol](model-context-protocol.md)).

The RAG lesson of module 2 over students keeps a service of the same shape, titled IA Devs - Sales Analytics Reporter with an empty referer, at temperature 0.7, with arcee-ai/trinity-large-preview:free as its only model and a provider sort by throughput ([model-routing](model-routing.md)). Its structured call builds the same agent and returns success with the structured response, or failure with the error's message when the call throws, printing nothing. The key comes from OPENROUTER_API_KEY and is never checked. The template builds the model whenever it builds the graph and never calls it, so it runs without a key, and its structured call takes the user prompt before the system prompt, the reverse of the final version. In the final version, every node but the extract question node and the executor calls it, so a simple question makes three calls, for the analysis, the query, and the answer, each asking for a json_schema response format with the agent's own name, extract, and strict on. The prompts are JSON objects written as compact text ([text-to-query](text-to-query.md)).

The document analysis lesson of module 2 keeps a service of the same shape, titled IA Devs - Document Q&A with an empty referer, at temperature 0.7, with the model list and a provider sort by throughput in every request ([model-routing](model-routing.md)). It builds a ChatOpenAI for google/gemini-2.5-flash-lite-preview-09-2025, a model that reads PDFs, and invokes it directly, without an agent, on two messages: the system prompt You are a helpful AI assistant that can analyze documents and answer questions about them., and one user message whose content holds the question as a text part and the uploaded PDF as an image_url part, whose URL is the whole file in base64 after data:application/pdf;base64,. It returns the answer's content as text with the model the response names, and when the call fails, it throws Multimodal generation failed: followed by the error's message. The key comes from OPENROUTER_API_KEY and is never checked. Without it, ChatOpenAI falls back to OPENAI_API_KEY, and with neither, every call fails before sending anything with the client's Missing credentials message, while an empty key still calls. The lesson declares **@langchain/community** without importing it, so the PDF is never parsed or split ([document-chunking](document-chunking.md)): the model reads it whole.

The multiple MCP tools lesson of module 3 reaches **OpenRouter** through one service with **@langchain/openai** 1.2 and **langchain** 1.2. It builds a single ChatOpenAI for the first of its models, arcee-ai/trinity-large-preview:free, at temperature 0.7 with at most 2048 tokens, and sends the whole model list and a provider sort by throughput with every request. The key comes from OPENROUTER_API_KEY, and a missing key only prints Assertion failed: OPENROUTER_API_KEY is not set in environment variables to standard error. Every call builds an agent with **langchain**'s createAgent from a system prompt and a user prompt: given a schema, the agent has no tools and asks for the provider's native structured output through providerStrategy, and otherwise it offers the MCP tools ([tool-calling](tool-calling.md)) and returns the text of its last message. The template's nodes never call it, while the final version's intent node asks for structured output and its agent node runs the tool loop. As published, the template's service imports a **LangChain** type as a value, which **Node.js** type stripping rejects, so npm start stops with a SyntaxError before printing anything. It runs through **tsx**, and the final version marks that import as type-only.

The Google Trends agent of module 3 keeps that service, titled IA Devs - Transforming Services into Tools. Neither of its nodes passes a schema, so every call offers the tools ([tool-calling](tool-calling.md)), returns the text of the agent's last message, and prints ✅ LLM Response: followed by the agent's whole final state as JSON. Its SerpApi key comes from SERPAPI_API_KEY and is checked the same way, so a missing key prints Assertion failed: SERPAPI_API_KEY is not set in environment variables.

The LangChain lesson of module 3 keeps the same service and passes no schema either, so its only call offers the MCP tools and prints ✅ LLM Response: with the agent's final state. With neither OPENROUTER_API_KEY nor OPENAI_API_KEY set, every call fails with the client's Missing credentials message before sending anything, while an empty key still calls and **OpenRouter** answers 401, and either way the graph retries until its recursion limit ([state-graph](state-graph.md)).

OpsPilot builds every model through one factory, which returns a new ChatOpenAI from **@langchain/openai** 0.3 on each call. The key comes from OPENROUTER_API_KEY, the model from OPENROUTER_MODEL or openai/gpt-4o-mini, the temperature is 0, and **OpenRouter**'s address is fixed in the code. The factory fails without the key, and the programs check the key before anything else. Strategies receive the factory instead of a model and ask it for a fresh instance for every agent, planner, replanner, and critic, so the tools bound for an agent never reach a structured call.

The planner, the replanner, and the reflection critic of [reasoning-strategies](reasoning-strategies.md) use structured output with **zod** schemas ([schema-validation](schema-validation.md)). In this version of the client, structured output is a function call: the request offers a single function named extract, whose parameters are the schema's JSON Schema, forces it through tool_choice, and parses the arguments of the call that comes back. Every caller treats a failed or invalid structured answer as a reason to fall back, never as an error. From unit 4, the learning reflector of [semantic-memory](semantic-memory.md) is one more structured caller, whose fallback is to learn nothing. From unit 5, a history summarizer calls the model with a system and a user message, without tools or structured output, and the strategies read the usage the client attaches to each model message ([context-management](context-management.md)).

Unit 6's factory returns a facade over a primary ChatOpenAI and an optional reserve, each with the client's own retries off and a callback that records the model that finished a call. Its methods bind tools, ask for structured output, or invoke through retries and the reserve, as [model-routing](model-routing.md) describes, and the prebuilt ReAct agent receives the facade in place of a chat model, binding the tools through it. A turn's router is one more structured caller ([reasoning-strategies](reasoning-strategies.md)), and its fallback is the react route.

The AIOps labs of module 6 share one model, built in core/llm_config.py: **CrewAI**'s LLM for groq/llama-3.1-8b-instant at temperature 0.2, which every agent of the crew calls ([agent-crew](agent-crew.md)). Its key is GROQ_API_KEY, which **python-dotenv** first loads from the .env file at the project's root, found by walking up from core/, without overriding a variable the environment already sets, even an empty one. Nothing checks the key: without one, the lab prints its header and **LiteLLM** calls **Groq** without an Authorization header, so the lab fails on the 401 with **Groq**'s Invalid API Key in the traceback, while an empty key fails before sending anything, because **httpx** refuses the header Bearer with its trailing space. **CrewAI** has no client of its own for **Groq**, so it hands the call to **LiteLLM**, which drops the groq/ prefix and posts to /chat/completions under **Groq**'s OpenAI-compatible address, https://api.groq.com/openai/v1, or under GROQ_API_BASE when it is set, with a bearer key, without streaming, and with the agent's tools. requirements.txt also declares **langchain-groq**, which no file imports.

The fifth UI/UX lesson's brag-bot reaches **Gemini** through **Genkit** 1.32 and its **@genkit-ai/google-genai** plugin, configured once with gemini-2.5-flash as the default model and the key from GEMINI_API_KEY, GOOGLE_API_KEY, or GOOGLE_GENAI_API_KEY. Its only flow, bragGeneratorFlow, turns a draft into a brag ([schema-validation](schema-validation.md)). It builds one Portuguese prompt that casts the model as a Senior Career Consultant for software engineers' individual development plans, asks it to turn the informal draft into an executive Brag Document, sets four rules (a professional tone without emotional adjectives, a plausible kind of metric when the draft gives none, the JSON schema strictly, and the draft's own language), and ends with the draft. It generates at temperature 0.8 with JSON output against the brag schema, so **Genkit** sends one generateContent request with the prompt as the only user message, application/json as the response type, and the schema, with each field's description, as responseJsonSchema. **Genkit** parses the answer and checks it against the schema, and the flow returns it with an id from **uuid**'s v4, or fails with Falha ao gerar o conteúdo when there is no output. The **Express** route that calls the flow answers every failure with the same 500 ([rest-api](rest-api.md)).

## What usually goes wrong in other languages

- The original always calls **OpenRouter**'s address. Transcriptions read the base URL from OPENAI_BASE_URL and fall back to https://openrouter.ai/api/v1, which is how verification points them to the recorded answers, as the copy that produced the cases does.
- **OpenRouter** names models with their provider in front, as openai/gpt-4o-mini, and that name travels unchanged in every request, where the cases check it.
- **LangChain** for **Python** sends structured output as a json_schema response format by default, while OpsPilot's recorded answers arrive as a call to extract. The tested transcription passes method function_calling with an OpenAI function definition named extract and validates the returned dictionary with **pydantic** itself, because a **pydantic** class passed directly names the function after the class and its parser then ignores the recorded call.
- Clients send different defaults beside the messages, such as top_p, the penalties, n, or stream. The cases check only the model and the temperature, plus tool_choice or the response format on structured calls. The module 3 lessons cap answers at 2048 tokens, which clients send as max_tokens or max_completion_tokens, so the cases leave that cap out.
- The multiple MCP tools lesson, the medical appointment lesson, and the song highlights final version ask for structured output as a json_schema response format named extract, with strict on, and parse the answer's content. **openai-go** sends the same through its JSON schema response format. The cases check the type and the schema's properties, descriptions, enum, and required fields, never the format's name or the types of the nullable fields, which **pydantic** writes as anyOf. The optional fields of the medical appointment lesson and of the song highlights lesson are not nullable, so the cases check their types, and the medical appointment message has a minLength of 10.
- The song highlights chat prompt's own examples give the preferences as null, which its schema rejects, so an answer that copies them leaves no structured response, and the turn apologizes with undefined as its error. The agent checks the answer against the JSON Schema, extra fields included, and returns it as it came, keys in the model's order, which the summary prompt sends back as the previous summary ([conversation-memory](conversation-memory.md)).
- These lessons and the Google Trends agent send the model list and the provider sort as extra fields of every request, and the cases check them. **openai-go** adds them with WithJSONSet, and the **Python** clients with extra_body.
- The multiple MCP tools lesson, the Google Trends agent, the LangChain lesson, the medical appointment lesson, and the song highlights lesson check their keys with console.assert, which prints and goes on. **Python**'s assert raises instead and disappears under -O, so a transcription prints the line to standard error itself and continues.
- The medical appointment lesson's prompts are JSON objects written as compact text, with the keys in the order the code declares them and the accents kept, and the cases compare them exactly. **Python**'s json.dumps needs separators without spaces and ensure_ascii off. The intent prompt's current date is UTC with milliseconds and a Z, as in 2026-10-27T09:50:11.797Z, which the cases check by that shape, and **Python**'s isoformat writes neither by itself.
- The agent of the medical appointment lesson returns no structured response when the answer does not fit the schema, so the message node fails reading it and answers its generic error, An error occurred while processing your request. The apology Desculpe, errei! comes only from a failed call. The tested **Python** transcription sends the response format itself and checks the content with a **pydantic** TypeAdapter over a TypedDict, which gives no answer when it does not fit.
- The **Python** OpenAI client refuses an empty key when it is built, while the JS client fails only when it calls, so the medical appointment lesson's server starts without a key. The tested transcription builds the client on its first call.
- With an empty key, the Google Trends agent and the song highlights final version still call the model and send Authorization: Bearer, because fetch trims the header's trailing space. The **Python** OpenAI SDK refuses an empty key when it calls, and **httpx** rejects a header that ends in a space, so the tested transcription of the Google Trends agent passes the key as a function and sends that header itself.
- A rejected key becomes an exception whose text depends on the client: the JS client adds a troubleshooting link, and the **Python** SDK starts with Error code. The cases only require the status code on its first line.
- The document analysis lesson sends the PDF as an image_url part with application/pdf in its data URL, where **OpenRouter** documents a file part for PDFs. The cases compare that part and its URL exactly, so a transcription builds it as a plain content part instead of a client's file or document block. **Ollama** rejects it as an invalid image, so the lesson needs a model that reads PDFs.
- The data URL holds standard base64 with padding and without line breaks. **Python**'s base64.encodebytes and **Java**'s MIME encoder break lines every 76 characters, so transcriptions use b64encode and Base64.getEncoder.
- That lesson answers No answer generated when the model's text is empty, because **JavaScript**'s || treats the empty string as missing, so a transcription checks for emptiness, never only for null.
- The AIOps labs reach **Groq** through **LiteLLM**, which reads GROQ_API_BASE before **Groq**'s own address. Transcriptions read the same variable and fall back to https://api.groq.com/openai/v1, and the cases point it to the replay. The request names llama-3.1-8b-instant without the groq/ prefix, and the cases check it with the temperature of 0.2.
- **LiteLLM**'s **Groq** client reads the service_tier field every **Groq** answer carries and fails without it, so the recorded answers include it with x_groq, as **Groq** documents them.
- The AIOps transcriptions load .env without overriding a variable already set, as **dotenv** for **Node.js**, **godotenv**, and **dotenvy** do by default, and the cases check the bearer key that results, writing .env and removing GROQ_API_KEY when they need to.
- Without any AIOps key, the cases accept a request without an Authorization header or with an empty bearer, and expect **Groq**'s Invalid API Key on standard error, so a transcription that checks the key and stops before calling fails them, and a client that refuses to build without a key, such as the **OpenAI** SDK for **Python**, needs the header left out by hand.
- brag-bot's plugin always calls https://generativelanguage.googleapis.com. Google's GenAI SDKs for **JavaScript**, **Python**, and **Go** read the address from GOOGLE_GEMINI_BASE_URL, other clients take it as a base URL option, and verification points that variable to the recorded answers, as the copy that produced the cases does by passing it to the plugin as baseUrl.
- The request goes to /v1beta/models/gemini-2.5-flash:generateContent under that address, with the key in an x-goog-api-key header. The cases check the single user message and its text, the temperature, the response type, and the schema's properties, descriptions, and required fields. **Genkit** sends the schema as responseJsonSchema, a JSON Schema, not as the older responseSchema, an OpenAPI subset with uppercase types, so transcriptions use response_json_schema in **google-genai** for **Python** and ResponseJsonSchema in **Go**'s genai.
- brag-bot's prompt is a template literal that starts with a line break and ends with a line break and four spaces. The cases accept any whitespace around it and compare the rest exactly, accents and quotes included.
- **Genkit** writes additionalProperties true into the schema it sends and checks, and the flow spreads the answer into its result, so fields the model adds beyond the schema reach the route's answer. The stand-in that recorded the cases added such fields, and the cases expect them. A typed decode into a struct or a **pydantic** model drops them, so a transcription checks the decoded object and returns it as it came, plus the id.
- An answer that is not JSON, or that lacks a field or gives one the wrong type, fails **Genkit**'s check and ends in the route's 500. The flow also checks its input before calling, so a definition that is a number or a list fails without a request, while one of spaces reaches **Gemini**.
- A missing key fails only when the flow calls the model, so the pages still render and the route answers 500 without a request. **Genkit** does not retry a 429 or a 503, so neither does a transcription.
