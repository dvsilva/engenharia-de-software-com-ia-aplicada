# LLM HTTP API

## Concept

A language model served locally or remotely answers HTTP requests. The OpenAI-compatible chat completion endpoint takes a list of messages with roles and returns the assistant's message plus token usage. A gateway such as **OpenRouter** serves the same endpoint for many providers' models, takes the key as a bearer token, and adds what only it knows to the answer, such as the provider that served the request and its cost ([model-routing](model-routing.md)). Anthropic's Messages API takes the same kind of list with a required token limit and answers with a list of content blocks, text and, only when the request enables it, thinking. **Gemini**'s Interactions API takes an input and the tools and answers a list of steps, such as thoughts, function calls, and model output, keeping the conversation on the server, with a status of requires_action while a call waits for its result. Its generateContent endpoint on **Vertex AI** lives under a Google Cloud project and region, takes an OAuth access token and contents made of parts, such as text and an image inline in base64, with a generation config that can require JSON, and answers candidates whose parts hold the text, with the token usage. A provider's native generation endpoint takes a single prompt and can stream the answer while it is produced, one JSON object per line, and its native chat endpoint takes the messages and the tools and answers one message that may carry thinking and tool calls, while its embedding endpoints turn texts into vectors. Local servers also manage models, listing what is installed and pulling new ones.

## How the course implements it

The **Ollama** example is a shell script. It lists the local models and pulls two of them (llama2-uncensored:7b and gpt-oss:20b) with the **Ollama** CLI. Then it asks the same question three times. The first request goes through the OpenAI-compatible chat completion endpoint with **curl**, and **jq** pretty-prints the whole response. The second goes through the native generation endpoint without streaming, and only the answer and the model's reasoning (the thinking field) are printed. The third streams the native generation and prints every chunk as it arrives. The script keeps the responses it got as comments: the uncensored model answers, and the reasoning model refuses and explains why.

The **OpenRouter** example that follows is a shell script too. It sources a .env file beside it for OPENROUTER_API_KEY and sends one chat completion to https://openrouter.ai/api/v1 with **curl**: google/gemma-3-27b-it:free, a single user message (Me conte uma curiosidade sobre LLMs), temperature 0.3, and at most 1000 tokens. The key goes as a bearer token, and two headers attribute the request to an app in **OpenRouter**'s rankings: HTTP-Referer with http://localhost:3000 and X-Title with My Example. **jq** pretty-prints the whole response, which the script keeps as a comment: the answer, the provider **OpenRouter** routed to (Google AI Studio), the native finish reason, and the usage with its cost. An error answer is printed the same way, and the script still exits with 0.

The ecosystem automation lesson of the project management module calls **Claude** through **@anthropic-ai/sdk** to parse a chat message into a card for its bot ([chat-bot](chat-bot.md)). It sends one Messages API request to claude-sonnet-4-6 with max_tokens 1024 and a single user message: a Portuguese prompt that describes the RouteWise project, its components, and its team, puts the message where the prompt says [COLE A MENSAGEM AQUI], lists the fields of the JSON it expects, and sets rules such as never inventing an assignee and describing implicit dates in words. The project's key comes from JIRA_PROJECT_KEY or ROUTEWISE when the bot starts. The bot reads the first content block's text, keeps everything from the first opening brace to the last closing brace, and parses it, so a code fence or a sentence around the JSON does no harm. Without any brace, it fails with Parser não retornou JSON válido. The key comes from ANTHROPIC_API_KEY.

The single-agent lesson of the AI systems architecture module reaches **Ollama** through its official client, **ollama** for **JavaScript** and for **Python**, with gemma4:e2b ([reasoning-strategies](reasoning-strategies.md)). Every call is a POST on the native chat endpoint without streaming: the anatomy demo sends one user message, or a question, its answer, and a critique, and the ReAct prototype sends its whole history with the tool. A transient failure gets up to three attempts ([model-routing](model-routing.md)), while a missing model, which **Ollama** answers with 404, fails at once. Its provedores-pagos file sketches the same call on three paid providers through their SDKs, each with the same tool ([tool-calling](tool-calling.md)): **Claude** on the Messages API with claude-sonnet-5, max_tokens 1024, and the conversation as messages, **Gemini** on the Interactions API with gemini-3.5-flash and the protocol alone as input, and **GPT** on chat completions with gpt-5.6 and the conversation as messages. The keys come from ANTHROPIC_API_KEY, GEMINI_API_KEY, and OPENAI_API_KEY.

The gateway prototype of the specific AI patterns lesson ([ai-gateway](ai-gateway.md)) uses the same clients in two other ways. Each answer streams from the native chat endpoint with stream true, one JSON object per line, and with gemma4 the thinking arrives first, in chunks whose message carries thinking and an empty content. Each embedding is a POST of nomic-embed-text and one text ([text-embeddings](text-embeddings.md)): to /api/embeddings with the text as prompt in **JavaScript**, whose answer holds embedding, and to /api/embed with the text as input in **Python**, whose answer holds embeddings, one vector per input.

The enterprise architecture lesson's three prototypes reuse those calls: the tiering prototype streams each tier's answer and embeds through the same two endpoints ([model-routing](model-routing.md)), while the eval gate ([model-evaluation](model-evaluation.md)) and the manipulation guardrail ([prompt-injection-defense](prompt-injection-defense.md)) ask without streaming. Only the answer's content counts, never its thinking.

The GRPO demo of the data processing and fine-tuning module ([verifiable-reward](verifiable-reward.md)) posts to **Ollama**'s native generation endpoint at a hardcoded http://localhost:11434, which the copy that produced its cases reads from OLLAMA_HOST instead, with the standard library's HTTP client, fetch in **JavaScript** and urllib in **Python**: gemma4:e2b, a single prompt, stream false, and the temperature under options. It reads only the response field, and any status other than success counts as a failed call.

The multimodal extraction tool of the dataset preparation lesson ([dataset-preparation](dataset-preparation.md)), in **JavaScript** with fetch and in **Python** with urllib, posts one generateContent request per document image to **Gemini** 2.5 Flash on **Vertex AI**, at https://us-central1-aiplatform.googleapis.com/v1/projects/{project}/locations/us-central1/publishers/google/models/gemini-2.5-flash:generateContent, which the copy that produced its cases reads from GOOGLE_VERTEX_BASE_URL instead. The project comes from GCP_PROJECT_ID, without which the tool refuses to start, and the bearer token from the output of gcloud auth print-access-token, run before every call. The single user content holds the prompt as a text part and the PNG as an inline_data part with its mime_type, and the generation config sets temperature 0 and responseMimeType application/json. The tool parses the first candidate's first part as JSON and reads promptTokenCount and candidatesTokenCount from usageMetadata. An error status or a failed gcloud counts as a failed document, and so does an answer without text or JSON in **JavaScript**, while **Python** ends with an unhandled error on one, so the cases never record such an answer.

The final project lesson of the same module calls its tuned models the same way, at /v1/ followed by the endpoint's full name, projects/{project}/locations/us-central1/endpoints/{id}, and :generateContent, read from ENDPOINT_MODULO32 and ENDPOINT_MODULO63 ([model-evaluation](model-evaluation.md)), with the instruction, a blank line, and the input as the only text part, temperature 0, and the first candidate's first part taken as plain text, since the caller parses it. Its assistant reaches the same endpoint through the model evaluation lesson's harness ([ai-gateway](ai-gateway.md)). An error status ends either program, reported as Falha ao chamar o modelo: with the status and its reason in **JavaScript** and as HTTP Error by **Python**'s urllib.

## What usually goes wrong in other languages

- The server address comes from the OLLAMA_HOST variable, falling back to http://localhost:11434, as the **Ollama** CLI and SDKs do. The variable may lack a scheme, so http:// is added when it is missing. This is also how verification points a transcription to the recorded responses.
- The CLI commands have HTTP equivalents: listing is a GET on the tags endpoint, and pulling is a POST on the pull endpoint with the model name. Languages without the CLI use the endpoints, and a pull streams progress lines until a final success status.
- To pull, the **Ollama** CLI sends the model in the older name field and leaves model empty, while the API documents model and the server accepts either, so transcriptions send model. Before every command, the CLI also checks that the server is running with a HEAD request on the root path, which transcriptions do not need.
- The native generation endpoint streams by default, so both calls send the stream flag explicitly, false for the single response and true for the stream.
- The native stream is newline-delimited JSON, while the OpenAI-compatible endpoint streams server-sent events. This module only streams from the native endpoint.
- The thinking field exists only for reasoning models, and it is printed as null when missing, as **jq** does. When such a model streams, its thinking arrives first, in chunks with an empty response, and the answer follows in chunks without the thinking field. The last chunk sets done to true and carries the done reason and the timings instead of text.
- Printing the whole response means serializing the parsed JSON with indentation. Key order and spacing may differ from **jq**, but the values may not, and non-ASCII characters, such as the curly apostrophe in the refusal, must stay as they are. **OpenRouter**'s answer carries fields the OpenAI format lacks, such as provider, native_finish_reason, and cost, and fields set to null, such as logprobs and refusal, so a typed response or an SDK that drops them fails the cases. Transcriptions of both examples use the plain HTTP clients in the table below.
- **curl** without --fail prints an error body like any other, such as the 401 for a key **OpenRouter** does not know, so transcriptions print the body whatever the status, without raising on it.
- The **OpenRouter** example sources .env, so its OPENROUTER_API_KEY line becomes a shell variable. Transcriptions read that file and fall back to the environment, and the cases write the same placeholder key to both.
- The original always calls **OpenRouter**'s address. Transcriptions read the base URL from OPENAI_BASE_URL and fall back to https://openrouter.ai/api/v1, which is how verification points them to the recorded answers, as the copy that produced the cases does.
- The script's quoting puts the model in single quotes ('google/gemma-3-27b-it:free'), which is not valid JSON. **OpenRouter** reads it anyway, as the documented answer shows, while stricter servers such as **Ollama** reject it. Transcriptions send valid JSON, and the cases read both alike. The original also misspells its content type as applicaton/json, which **OpenRouter** ignores, so transcriptions send application/json and the cases do not check it.
- **OpenRouter** documents X-OpenRouter-Title and keeps X-Title for backward compatibility. Transcriptions send X-Title as the original does, because the cases answer only when the bearer token, HTTP-Referer, and X-Title carry the original's values.
- Pulling these two models downloads about 17 GB when they are missing. Pulling a model that is already installed only verifies it.
- The **Anthropic** SDKs read ANTHROPIC_BASE_URL, which is how verification points the ecosystem automation lesson to the recorded answers. A client written by hand posts to /v1/messages under that address with the key in an x-api-key header and an anthropic-version header. **@anthropic-ai/sdk** 1.3 sends the key as a bearer token instead, so the cases only require an anthropic-version header.
- The original sends the prompt as a string, and SDKs such as **anthropic-sdk-go** always send a list of content blocks. The API treats one text block like the string, and the cases accept either.
- The first content block holds the text because the request never enables thinking. **Ollama** adds a thinking block by default for models that can think, so the recorded answers come from a stand-in with thinking disabled.
- The pattern that finds the JSON is greedy and spans lines: [\s\S]* in **JavaScript**, re.DOTALL in **Python**, and (?s) or [\s\S] in **Go**'s RE2. Two separate objects in one answer join into invalid JSON, which ends in the error reply.
- **ollama-js** 0.6 ignores OLLAMA_HOST and always calls http://127.0.0.1:11434, while **ollama** for **Python** reads it. Transcriptions read OLLAMA_HOST, as the copy that produced the single-agent cases does.
- The native chat endpoint streams by default too, so the single-agent calls send stream false. **ollama** for **Python** also sends an empty tools list on calls without tools, which the cases accept.
- **Ollama**'s 404 for a missing model reads model 'gemma4:e2b' not found, and **ollama** for **Python** appends (status code: 404) to it. The legacy /api/embeddings endpoint words it as model "nomic-embed-text" not found, try pulling it first.
- /api/embeddings is the legacy endpoint and /api/embed the current one, and the gateway's two versions use one each, so its cases accept either. A transcription that embeds through the OpenAI-compatible /v1/embeddings fails them.
- The native endpoints take sampling settings such as the temperature inside an options object, while chat completions take them at the top level.
- **Python**'s urllib raises on any error status, while fetch, **Go**'s net/http, and **Rust**'s **reqwest** hand the error back as a response, so the GRPO demo's **JavaScript** version checks the status itself and a transcription in those languages does too.
- The **Gemini** SDKs read GOOGLE_GEMINI_BASE_URL and post the interaction to /v1beta/interactions with the key in an x-goog-api-key header. Their output_text joins the text of the model output steps after the last user input, which a client written by hand reads from the steps itself.
- **Vertex AI** takes the token gcloud prints, so transcriptions run gcloud auth print-access-token, as both originals do, and the cases answer that command with a stand-in that prints a recorded token, which every call must send as a bearer token. A gcloud that fails, as without an active account, fails each document. Google's auth libraries read application default credentials instead and never run gcloud, so they fail the cases.
- The **Vertex AI** address comes from GOOGLE_VERTEX_BASE_URL, falling back to the regional endpoint, as **google-genai** reads it for **Vertex AI**, and the cases point it to the recorded answers. The REST API accepts inline_data and mime_type or inlineData and mimeType, which the SDKs send, and the cases accept both.
- The **JavaScript** version checks the status and **Python**'s urllib raises on an error status, and both print the error body after Vertex AI retornou and the status, so a transcription reads the body of an error answer too.
- The answer's text is JSON because the request sets responseMimeType, so the tool parses it whole, without looking for braces. Its usage may lack a count, which **JavaScript** prints as null and **Python** as None, and the recorded answers always carry both.
- **JavaScript** checks GCP_PROJECT_ID when the module loads and **Python** when it is imported, so both stop before any document, with an unhandled error.
- The **OpenAI** SDKs refuse to load without OPENAI_API_KEY, and **google-genai** for **Python** without GEMINI_API_KEY, so provedores-pagos fails as soon as it is imported without its keys, and the cases set placeholders.

## How close common targets get

Every target has an HTTP client and JSON support, so every target is a direct equivalent. Transcriptions stay consistent by using these libraries:

| Target                            | **Ollama** and **OpenRouter**                                  | **Anthropic** Messages API                             | **Gemini** Interactions API                                           |
| --------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- |
| **Python**                        | **requests** and the standard json module                      | **anthropic**                                          | **google-genai**                                                      |
| **Go**                            | The standard library (net/http and encoding/json)              | **anthropic-sdk-go**                                   | net/http and encoding/json against /v1beta/interactions               |
| **JavaScript** and **TypeScript** | The built-in fetch                                             | **@anthropic-ai/sdk**                                  | **@google/genai**                                                     |
| **Rust**                          | **reqwest** with blocking and JSON support, and **serde_json** | **reqwest** and **serde_json** against /v1/messages    | **reqwest** and **serde_json** against /v1beta/interactions           |
| **C#**                            | HttpClient and System.Text.Json                                | The official **Anthropic** library for .NET            | HttpClient and System.Text.Json against /v1beta/interactions          |
| **Java**                          | The built-in HTTP client and **Jackson**                       | **anthropic-java**                                     | The built-in HTTP client and **Jackson** against /v1beta/interactions |
| **C++**                           | **libcurl** and **nlohmann/json**                              | **libcurl** and **nlohmann/json** against /v1/messages | **libcurl** and **nlohmann/json** against /v1beta/interactions        |

The single-agent lesson's **Ollama** calls use **ollama** in **Python** and **JavaScript**, as the originals do, and the first column elsewhere, and provedores-pagos reaches **GPT** with the official **openai** SDK in **Python** and **JavaScript** and with the first column's client against /v1/chat/completions elsewhere.

The multimodal extraction tool and the final project's tuned endpoint calls reach **Vertex AI** with the first column's client in every target, against the generateContent path, and run gcloud with the target's process API.

The **OpenRouter** example's .env file is read with **python-dotenv** in **Python**, **godotenv** in **Go**, process.loadEnvFile in **Node.js**, **dotenvy** in **Rust**, **DotNetEnv** in **C#**, and **dotenv-java** in **Java**, and **C++** splits each line at the first equals sign.

Tested transcriptions of the **Ollama** example exist for **Go** and **C#**, and of the **OpenRouter** example for **Python**. The tested **Go** transcription of the ecosystem automation lesson, with **anthropic-sdk-go**, sits with the chat-bot examples, the tested **Go** transcription of the single-agent lesson, which also reaches **Ollama**'s native chat and the **Gemini** Interactions API, with the reasoning-strategies examples, and the tested **Rust** transcription of the GRPO demo, with **reqwest**, with the investment-analysis examples.
