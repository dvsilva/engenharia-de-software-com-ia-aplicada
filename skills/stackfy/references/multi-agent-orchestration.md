# Multi-agent orchestration

## Concept

A multi-agent system splits a task among specialized agents and coordinates them through an orchestration pattern. The lesson's selector names six: sequential when one task needs another's result, parallel when independent tasks run at once and an aggregator collects them, supervisor when a central agent decides which specialist to call, hierarchical when supervisors manage other supervisors, group chat when agents with equal authority debate, and handoff when a task changes owner midway. Agents talk through messages on a bus or queue instead of calling each other: the publisher emits an event and moves on, and every subscriber reacts. A rich event carries the data its subscribers need, while a notification event only says that something happened, so subscribers fetch the data elsewhere.

A supervisor can also be a model that, each round, reads the request and a blackboard, a working memory every role appends to, and names the next role and a brief for it, until it closes with an answer. A cap on delegations bounds that loop the way a timeout bounds a hung agent, and giving each role only the tools its job needs makes least privilege structural, since a role cannot misuse a tool it was never given, whatever its prompt says.

Distribution brings partial failures, which call for two different mechanisms. Technical failures during execution follow the CAP theorem: the caller enforces an explicit timeout from outside, so it never depends on a hung agent to report itself, retries a limited number of times and then proceeds without the result, choosing availability over consistency, and keys every write by the request, so a retry is idempotent and never duplicates a document. Content problems found after the work succeeded follow the saga pattern: shared data is versioned, each result records the version it used and the version current when it finished, and a supervisor that finds the two different compensates by redoing only the stale part, preserving whatever was already right.

## How the course implements it

The multi-agent lesson of the AI systems architecture module prototypes TrialForge's four agents, Protocolo, ICF, CSR, and Supervisor, in **JavaScript**, the official version, and in **Python**, its mirror, with only the standard library and no LLM. Each agent is a function that waits for a fixed time and returns a record: 300 ms for the Protocolo, 450 ms for the ICF, and 600 ms for the CSR, the lesson's 30, 45, and 60 seconds divided by 100. Each timeout is 1.5 times its agent's time (450, 675, and 900 ms), a hung ICF waits three times its timeout, and a retry makes at most three attempts.

The bus is **Node.js**'s EventEmitter in **JavaScript**, whose emit calls the listener at once, and a minimal Barramento in **Python**, whose emit schedules the listener as an asyncio task. Every flow builds its own bus, versioned protocol state, document store, and execution log, and subscribes the parallel reaction once to protocolo:pronto before the Protocolo agent starts. That agent logs protocolo and emits a rich event with a copy of the protocol's version and criteria (a minimum age of 13) plus the study. When the flow asks for an ethics amendment, it also schedules one for 500 ms later, after the ICF finishes and before the CSR does, which archives the current version and criteria with a reason, increments the version, and lowers the minimum age to 12.

The parallel reaction starts the ICF and the CSR together, each logging its start before it waits and each bounded by its timeout: a promise raced against a timer in **JavaScript**, and asyncio.wait_for, which cancels the agent, in **Python**. Each agent's text names the minimum age and the version it received, and its record keeps both plus the live version when it finishes. The ICF registers its document under the protocol version before a forced failure, so a lost confirmation leaves the document stored, and the store counts another attempt instead of adding a second document. The reaction then joins the two results in one of two ways. Failing fast, with Promise.all or gather without return_exceptions, loses the CSR's result at the ICF's failure, which is the lesson's documented bug. Waiting for both, with Promise.allSettled or gather with return_exceptions, keeps each result or error.

The Supervisor applies the CAP mechanism first. With both results it decides nenhum_retry_necessario, with only the CSR's it retries the ICF alone, and with neither it decides retry_ambos, which nothing executes. The retry runs the ICF up to three times under the same timeout. A transient failure clears on the first attempt, while a persistent one repeats the forced failure or hang every time, so the Supervisor ends with retry_icf_executado_com_sucesso or retry_esgotado_seguindo_sem_icf and an unsuccessful reaction. When both results exist, the saga follows: any agent whose two versions differ is stale and is regenerated alone, one after the other, from the current version, and the decision becomes saga_compensacao_ followed by the stale agents, joined by _e_ and lowercased.

The program takes no input. It first runs ten self-checks, printing an [OK] or [FALHOU] line for each and a total, and a failed one stops it with exit code 1 before the demo. The demo narrates five scenarios: the happy path with the event, both results, the decision, and the execution order, the fail-fast join, the settled join with its single document and two attempts, the amendment that leaves only the CSR stale, and the hung ICF that recovers on the first retry, followed by the persistent hang that exhausts all three. A run takes about 20 seconds.

The versions differ only where the text names the language's own mechanism (Promise.all, Promise.allSettled, and Promise.race against gather() without and with return_exceptions and wait_for, and EventEmitter against Barramento sobre asyncio in the title), in their keys, camelCase in **JavaScript** and snake_case in **Python**, in how records print, through util.inspect over several lines when long or through repr on one line, in booleans, and in the timeout, 675ms against 0.675s.

Unit 9 of OpsPilot, the last lesson of the autonomous agents module, turns the on-call copilot into a team, in **TypeScript** with **LangGraph** 0.2 and **LangChain** over **OpenRouter** ([state-graph](state-graph.md), [chat-model](chat-model.md)). The team is a fourth strategy that the chat API's router can pick or the chat body can force ([reasoning-strategies](reasoning-strategies.md)), and it runs a supervisor and three roles, the analista, the planejador, and the executor, one at a time over a blackboard that lives for the turn. Only the roles append to it. Each entry holds the role, a kind (facts for the analista, plan for the planejador, execution for the executor, and error when a role fails), the brief that asked for it, and the content. The blackboard renders as its entries separated by a blank line, each a line with [n], the role, the kind in parentheses, an em dash, and brief: followed by the brief, then the content on the next lines, or as (blackboard vazio — nenhuma contribuição ainda) when it is empty.

Each round, the supervisor asks the model for a decision as structured output: next, one of analista, planejador, executor, or done, and brief, the work order for that role or the closing summary. Its system prompt holds a table of when to choose each step and what it delivers, and rules that suggest the order analista, planejador, executor, done, skipping roles that are not needed, and mention the ceiling of eight delegations. Its user message gives the request after Pedido do plantonista:, the delegations used after Delegações já usadas:, a blank line, and Blackboard: above the rendered blackboard. Every decision adds one handoff event to the trace, signed by the supervisor as its node, with the next step in to and the brief as its content.

The roles are restricted by the tools they receive rather than by their prompts ([tool-calling](tool-calling.md)). The analista, told to report facts and never propose or change anything, runs **LangGraph**'s prebuilt ReAct agent with list_alerts, list_incidents, consultar_runbook, and check_provider_status. The planejador makes one call without tools that turns the blackboard into a numbered plan. The executor runs the prebuilt agent with open_incident, resolve_incident, and list_incidents, built by the same factories over the same store as the other strategies' tools, and a held request still waits for approval at the API before any role runs ([agent-observability](agent-observability.md)). Each role's user message gives the original request after Pedido original do plantonista:, the brief after Sua tarefa (brief do supervisor):, a blank line, and Blackboard atual: above the rendered blackboard. A tool role's events come from its messages as ReAct's do, its entry holds its last answer, its recursion limit is 18, and its LLM calls are the model messages of its run. The planejador's entry holds its reply, and its single event is a plan. Every role signs its events with its own name as their node, and the production graph keeps those nodes instead of stamping the route on them.

The team graph starts at the supervisor, whose conditional edge goes to the chosen role or to done, and every role returns to the supervisor. Before asking the model, the supervisor counts the delegations, and at eight it hands off to done with teto de handoffs atingido: encerrando com o conteúdo do blackboard, without a call. A decision that fails or does not fit its schema hands off to done with decisão inválida do supervisor: and the error. A role that throws leaves an error entry whose content is erro no papel, the role, a colon, and the error, adds an observation with the same text signed by the role, and returns to the supervisor, so a failing role never fails the turn. The done node answers with the closing brief, trimmed, when there is one, else with Resumo do blackboard: above the rendered blackboard, else with A equipe encerrou sem contribuições no blackboard para: and the request, and adds that answer as an event signed by the supervisor. The team's LLM calls add one for every decision the supervisor asked the model for, a failed one included, and the calls of every role that finished. When the conversation has history, the team's request is Histórico recente da conversa:, one line per message with its role, a colon, and its content, a blank line, and the message, so the supervisor and every role see it. The unit's closing exercise, a consensus of two independent opinions and a structured judge, is not implemented.

## What usually goes wrong in other languages

- **JavaScript** and asyncio run every agent on one thread, so the protocol state, the document store, the execution log, and the bus need no locks. **Go**, **Java**, **C#**, **C++**, and **Rust**'s multi-threaded runtimes run agents in parallel while the amendment's timer writes the version they read, so each shared piece needs a mutex or a single owner. **Go**'s race detector catches the omission.
- A promise that loses a race keeps running, so a hung ICF in **JavaScript** registers its document after the flow has moved on, while **Python**'s wait_for cancels it. **Go** goroutines and **Java**'s orTimeout and **C#**'s WaitAsync also leave the work running, **Rust**'s tokio::time::timeout drops it, and a **C++** future from std::async blocks in its destructor until a hung task finishes. No printed result depends on it, because every flow owns its store, but a hung agent must never block the caller past its timeout.
- Promise.all and gather report the first error at once and leave the sibling running. **C#**'s Task.WhenAll, **Java**'s CompletableFuture.allOf, and **Go**'s errgroup wait for every task before failing, and **Rust**'s try_join! returns at once but cancels the sibling, so the fail-fast join returns at the first error received and discards the other result, as the originals do.
- The parallel reaction subscribes before the event fires and handles it once. A bus that dispatches on another thread must still log the ICF's start before the CSR's, which a pair of goroutines or threads launched together does not guarantee, so each agent logs its start before its task launches.
- The event carries a copy of the protocol state. A reference, or a **Go** map or pointer shared with the state, lets the amendment rewrite the criteria an agent already received and hides the divergence the saga must find.
- Each agent reads the live version when it finishes, not when it starts, which is what makes the CSR stale after the amendment.
- The ICF registers its document before the forced failure. Registering after it leaves one attempt instead of two, which a self-check catches.
- A failed self-check must exit with 1, as both originals do, so a **Rust** transcription exits explicitly instead of panicking with 101.
- Records print the way each language shows them, so other targets print JSON with the fields in the original's order, which a **Go** map or a **Java** HashMap would reorder, and **C++** needs std::boolalpha to print booleans as words.
- OpsPilot's supervisor reads its decision through a forced function call, as the router does ([reasoning-strategies](reasoning-strategies.md)). Arguments outside the schema, such as a role that does not exist, fail inside the model's runnable, so the call is retried once before the team closes, and an answer that calls no function closes it after one call.
- The cap is checked before the supervisor asks the model, so reaching it costs no call and adds no LLM call, and only delegations count toward it, never the closing decision.
- The team catches a role's failure and the supervisor's, so a provider that fails during a team turn still answers 200, where the other strategies answer 503 model_unavailable ([model-routing](model-routing.md)). The error's text is the client's own, which differs between libraries.
- Each role sees only the request, its brief, and the rendered blackboard, never another role's messages or tool results, so the analista's facts reach the planejador only through the analista's last answer.
- The roles' tool lists are separate, in the original's order, and the cases compare the tools each request offers, so a target that hands every role the same toolset fails them.
- The handoff and role events keep the node that produced them, so a target that stamps the route's name on every strategy event, as the production graph does for the other routes, loses the roles.
- The audit stores each event's type, node, and content plus a fixed list of other fields that leaves out to ([agent-observability](agent-observability.md)), so GET /requests/:id answers a team turn's handoffs without their destination, while the chat answer has it. The cases expect both, so a target that stores every field fails them.

## How close common targets get

Every target has timers, concurrent tasks, and a way to wait for several of them, so every target is a direct equivalent except **C++**, whose futures need care.

| Target                            | Fit               | Library                                                                                    |
| --------------------------------- | ----------------- | ------------------------------------------------------------------------------------------ |
| **Python**                        | Direct equivalent | asyncio from the standard library                                                          |
| **JavaScript** and **TypeScript** | Direct equivalent | **Node.js**'s EventEmitter and promises                                                    |
| **Go**                            | Direct equivalent | Goroutines, channels, select, sync, and time from the standard library                     |
| **Rust**                          | Direct equivalent | **tokio**, with tokio::sync and tokio::time                                                |
| **C#**                            | Direct equivalent | Task, Task.WhenAll, WaitAsync, and an event or a Channel                                   |
| **Java**                          | Direct equivalent | CompletableFuture with orTimeout on an ExecutorService                                     |
| **C++**                           | Substitute        | std::thread with std::promise, std::future::wait_for, and std::mutex instead of std::async |

OpsPilot's team runs one role at a time, so it needs none of these: a target uses the model clients and agent loops that [reasoning-strategies](reasoning-strategies.md) lists and the graph that [state-graph](state-graph.md) lists, or a loop over the supervisor's decisions written by hand.

A tested **Go** transcription of the message-queue prototype exists.

## Tolerance

The prototype calls no model and draws no random numbers, and at least 50 ms separate the events that decide each outcome, so the cases compare everything exactly, in either original's wording. Where the text names the language's own mechanism, any name is accepted. Records are accepted as util.inspect, repr, or JSON, with camelCase or snake_case keys in the original's order and booleans in either case, and the timeout as 675ms or 0.675s. Durations are never printed, and the cases pass repeatedly with several runs at once.

OpsPilot's team turns replay recorded model answers and are compared as its other chat turns are ([reasoning-strategies](reasoning-strategies.md)), except two texts that come from libraries: a decision outside the schema, checked by the prefix decisão inválida do supervisor:, and a role's provider error, checked by its status code and the provider's message, inside the trace, the blackboard, and the prompts that carry it.
