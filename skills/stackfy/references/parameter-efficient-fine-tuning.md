# Parameter-efficient fine-tuning

## Concept

Full fine-tuning updates every weight of a model, so it needs memory for the weights, their gradients, and the optimizer's state, and saves a checkpoint as large as the model. Parameter-efficient fine-tuning (PEFT) freezes the base model and trains a few new parameters instead. LoRA (Hu et al., 2021) adds to chosen linear layers a low-rank update, the product of a d×r and an r×k matrix scaled by a factor, so a d×k layer gains r(d + k) trainable parameters and doubling the rank r doubles them. The adapter is saved apart from the base model, in megabytes instead of gigabytes, and loaded over it at generation, so one base model serves many adapters. QLoRA (Dettmers et al., 2023) quantizes the frozen base to 4-bit NF4 and trains the adapters in 16 bits, which cuts memory at a small cost in quality, and DoRA (Liu et al., 2024) decomposes each weight into a magnitude and a direction and trains both, at a small extra cost in parameters.

The rank trades quality for size: a higher rank fits the task better, with diminishing returns, while peak memory barely moves, because the frozen base dominates it. Training is watched through the validation loss at intervals. A loss still falling sharply at the last point means the run stopped too early, a loss above its minimum means overfitting, and early stopping keeps the best iteration. The scale of the update has no common definition: **MLX-LM** multiplies it by a scale, **PEFT** by lora_alpha divided by the rank, and managed APIs take their own lora_alpha, so neither those values nor the learning rates compare across frameworks, while the final validation loss does.

## How the course implements it

The LoRA and PEFT lesson of the data processing and fine-tuning module trains rank 4, 8, and 16 adapters on mlx-community/gemma-4-e2b-it-bf16, about 4.63 billion parameters, with the 200 Amplitude Seguros extraction examples of the fine-tuning via API lesson ([model-fine-tuning](model-fine-tuning.md)). Training runs **MLX-LM**'s command line, python3 -m mlx_lm lora, with one YAML file per rank: 20 iterations, batch 1, learning rate 1e-5, 16 layers, scale 20, dropout 0, seed 0, and an adapter folder each, mlx-adapters for rank 8 and mlx-adapters-rank4 and mlx-adapters-rank16 for the others, which the lesson ships with their weights. Its tools are written in **JavaScript** and mirrored in **Python** with only the standard library, each running self-checks first, an [OK] or [FALHOU] line per check and a total, before its demo, as the module's other tools do ([decision-framework](decision-framework.md)). None of them trains: **MLX-LM** has no **Node.js** binding, so the tools that use it run it as a process.

The local training tool prepares the data and the analysis around a run. It converts each example of ../modulo-03-fine-tuning-via-api/dataset-treinado.jsonl, **Vertex AI**'s contents with a user and a model turn, into **MLX-LM**'s messages with a user and an assistant turn, rejecting an example without either turn before writing anything. It then splits the examples by person, the segurado or beneficiario of the model turn's JSON, so nobody lands in two splits: the validation and test quotas are 15% and 5% of the total, rounded, the groups are ordered by size and then by name, each group goes to the test split while it is below its quota, then to validation, and otherwise to training, and the examples without a person go to the end of training. It writes mlx-data/train.jsonl, valid.jsonl, and test.jsonl, one JSON object per line, 157, 30, and 13 examples for the lesson's data, and prints the source and destination paths and the counts. Its other functions validate the hyperparameters (iters and batch size positive integers, a learning rate in (0, 1], and a fine-tune type of lora or full), build the arguments of mlx_lm lora, read each Iter N: Val loss X line of its output, and analyze a curve: the best iteration has the lowest loss, the relative drop between the last two points above 3% means it is still falling sharply, and a last loss more than 3% above the best, at an earlier iteration, means overfitting. The demo applies that analysis to the real 20 and 120 iteration curves, written in the tool, and finds the first undertrained and the second best at iteration 90.

The adapter comparison tool takes the example at index 8 of mlx-data/test.jsonl, a medical receipt, and runs python3 -m mlx_lm generate with the model, the prompt, and 80 tokens at most, first without an adapter and then with --adapter-path pointing to the mlx-adapters folder beside the program. From each output, standard output and standard error joined, it takes the text between the first two lines of equals signs, trimmed, and the count after Generation:, parses the text as JSON, and compares it field by field with the example's answer. Without the adapter the model spends its 80 tokens thinking aloud, printed up to 220 characters, and never answers, and with it the answer is exact in 28 tokens. A failed run ends the tool with mlx_lm's message. The rank comparison tool does the same for a workshop estimate whose total follows two distracting amounts, without an adapter and with each rank, where every rank finds the exact answer in 27 tokens. It reports a failed configuration with mlx_lm's message and goes on, counts the failures, and stops with an error only when every configuration failed.

The rank trade-off tool prints the three real runs: trainable parameters (3.408, 6.816, and 13.631 million, up to 0.295% of the model), validation loss from 4.752 to 1.246, 0.895, and 0.725, peak memory around 10.8 GB, speed, and adapter size. It derives what each doubling of rank costs and returns, recommends the smallest rank within 10% of the best loss, rank 16, and compares QLoRA with bf16 at rank 8 (65% less disk, 61.3% less training memory, 4.1% worse loss) and DoRA with LoRA (1.07 times the parameters, 0.266 GB more memory, the same loss). The full fine-tuning tool adds a full run of the same model, 22.567% of its parameters on the same 16 layers, loss 0.612, 15.338 GB, and a 1,992 MB checkpoint, and rejects it because it beats the best LoRA by 15.59%, below a 20% threshold.

The lesson's **Hugging Face** script, in **Python** only, trains the same rank 8 adapter on a CUDA GPU with **transformers**, **peft**, and **trl**. It loads google/gemma-4-E2B-it in 4-bit NF4 through **bitsandbytes**, attaches a LoraConfig of rank 8, lora_alpha 16, and dropout 0 to every linear layer, trains 20 steps of **trl**'s SFTTrainer at a constant 2e-4 with a collator that applies the chat template and masks padding with -100, evaluates once, saves the adapter, and answers a hard example greedily. It refuses to load the model when **PyTorch** sees no CUDA device, and its --test flag runs nine checks that need no GPU: the hyperparameter ranges, the 157, 30, and 13 examples in mlx-data, and the rank and step budget. Two **Google Colab** notebooks repeat that training with the splits inline, one with a memory breakdown per phase and its own prepare_model_for_kbit_training that skips upcasting Gemma 4's 2.35 billion element per-layer embedding, and the other as full fine-tuning of a smaller Qwen model with an 8-bit AdamW and gradient checkpointing. The lesson also prices local LoRA against a rented GPU ([investment-analysis](investment-analysis.md)) and sends the same LoRA settings to a managed API ([model-fine-tuning](model-fine-tuning.md)).

The final project lesson serves the rank 8 checkpoint to its assistant ([ai-gateway](ai-gateway.md)) through chamar_modelo_local.py, a companion in **Python** only. It reads the instruction and the input as JSON from standard input, loads mlx-community/gemma-4-e2b-it-bf16 with ../modulo-04-lora-e-peft/mlx-adapters through mlx_lm's load, applies the chat template to one user turn holding the instruction, a blank line, and the input, generates 150 tokens at most with mlx_lm's generate, greedy by default, and prints the raw answer without parsing it. It answers the Demo's workshop estimate, whose total follows two partial amounts, with the exact fields, and a medical receipt with the amount as the text R$ 350,00. Its **Hugging Face** twin, chamar-modelo-local-hf.py, keeps the same contract with **transformers** and **peft**: it loads google/gemma-4-E2B-it in 4-bit NF4 and the adapter in gemma-amplitude-lora-colab-adapter beside it, decodes only the generated tokens, greedily, and stops with a FileNotFoundError naming that folder, before importing any library, when the adapter is missing. A **Google Colab** notebook trains that adapter with the lesson's QLoRA recipe, saves it, and reloads it from disk as a new process would, and its recorded runs answer the Demo's 1870.5 as 187050 four times in four, a reproducible failure of that checkpoint on decimal amounts it never saw.

## What usually goes wrong in other languages

- Training and generation stay in **MLX-LM**'s process, started as python3 -m mlx_lm with the same arguments, so a transcription in any language runs that command instead of a library, and the cases answer it with a stand-in first on PATH. A **Python** transcription started as python3 also reaches that stand-in, which lets that launch through to the installed python3.
- The prompt goes as one argument with its line breaks, never through a shell, and the adapter path is absolute, the folder beside the program, which the cases expect inside the transcription's folder. A **Go** program started with go run lives in a temporary folder, so it takes the working directory instead.
- mlx_lm writes its progress bars to standard error and the answer and Generation: line to standard output, so the tools join both before parsing, and a failed run reports standard error. Reading only one stream loses either the count or the message.
- **MLX-LM** 0.32 reports training as a table, with lines such as val 4.758, instead of the Iter N: Val loss X lines the training tool reads, so its parser finds nothing in that version's output.
- The split breaks ties by name, which **JavaScript** compares with localeCompare and **Python** by code point. They agree on the course's names, unaccented and capitalized, and a code-point comparison, as **Go**, **Rust**, and ordinal string comparison in **C#** and **Java** do, keeps that agreement. The quotas round a half up in **JavaScript** and to even in **Python**, which no dataset of the lesson reaches.
- The tools print numbers in **JavaScript**'s shortest form after rounding with toFixed, as 10.93 GB and a gain of 0.17, while some lines keep three decimals, as 10.930 GB, and **Python** mirrors each case. **Python** writes the splits with a space after each colon and comma and prints booleans as True and False and parsed JSON with spaces, and the cases accept either.
- The **Hugging Face** script sets PYTORCH_CUDA_ALLOC_CONF before importing **PyTorch**, which reads it only at import. On Apple Silicon, torch.cuda.is_bf16_supported returns False and the memory counters return 0 instead of failing, and **bitsandbytes** 0.50 quantizes to 4 bits and steps an 8-bit AdamW on MPS, so the notebooks start in float16, but loading their model with device_map="auto" stalls on MPS with **transformers** 5.21 and **PyTorch** 2.14, while loading it on the CPU and moving it to mps takes seconds.
- The final project's **Hugging Face** companion and its notebook load the model the same way, with device_map="auto", so they need a CUDA GPU as well, and the companion's adapter exists only after the notebook runs on one.
- The final project's companion writes only the model's answer to standard output, which its caller parses, so nothing else may print there, and mlx_lm's generate with verbose=False prints nothing. Serving the checkpoint from another runtime, such as **Ollama** with the adapter in a Modelfile or **llama.cpp** after fusing it, changes the precision and the template, so its answers are no longer the checkpoint's.

## How close common targets get

The tools only read files, run mlx_lm, and compute, so every target is a direct equivalent for them. Training or generating inside the program's own process, as the **Hugging Face** script, the notebooks, and the final project's companions do, exists only in **Python**, and other targets run mlx_lm or those scripts as a process, or explain them instead of transcribing them.

| Target                            | Fit               | Library                                                                                           |
| --------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------- |
| **Python**                        | Direct equivalent | subprocess for mlx_lm, and **transformers**, **peft**, **trl**, and **bitsandbytes** for training |
| **JavaScript** and **TypeScript** | Direct equivalent | child_process.spawnSync for mlx_lm, as the originals                                              |
| **Go**                            | Direct equivalent | os/exec with separate buffers for both streams, and encoding/json                                 |
| **Rust**                          | Direct equivalent | std::process::Command's output, and **serde_json**                                                |
| **C#**                            | Direct equivalent | System.Diagnostics.Process with both streams redirected, and System.Text.Json                     |
| **Java**                          | Direct equivalent | ProcessBuilder, reading both streams on their own threads, and **Jackson**                        |
| **C++**                           | Direct equivalent | posix_spawnp with two pipes drained by poll, and **nlohmann/json**                                |

A tested **Rust** transcription of the two comparison tools exists, running mlx_lm with std::process::Command.

## Tolerance

The tools' numbers are written in them, and the stand-in prints what mlx_lm printed, so every output and split is compared exactly, apart from the spellings the originals differ in. The answers come from real runs of mlx-lm 0.32.2 on the lesson's adapters, which repeated the lesson's token counts and answers, while the base model thought aloud in other words, and greedy generation repeats them on the same versions. Training is not reproduced by the cases: a rerun of the lesson's rank 8 YAML went from 4.758 to 0.898 at iteration 20, against the lesson's 4.752 and 0.895, within the 2.3% the lesson measures between runs. The final project's companion is compared byte for byte with the answers mlx-lm 0.32.2 gave on the rank 8 adapter, which repeated in every run.
