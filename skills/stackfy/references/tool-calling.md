# Tool calling

## Concept

Tool calling lets a model act instead of only answering. The request describes each tool by name, a description, and a JSON Schema of its arguments. The model may answer with one or more calls, each with an id, a tool name, and its arguments as a JSON string, instead of text. The program validates the arguments, runs each tool, and sends every result back as a tool message tied to the id of the call it answers, and the model is called again with the whole conversation until it answers in text. Tools return text the model reads, and predictable failures come back as text too, so the model can recover instead of the program crashing. Providers declare the same tool in different shapes: the OpenAI format nests the name, description, and parameters under function, **Anthropic** puts them at the root with the schema as input_schema, and **Gemini**'s Interactions API at the root with a type of function.

## How the course implements it

The multiple MCP tools lesson of module 3 gives its agent the tools of MCP servers ([model-context-protocol](model-context-protocol.md)) through **langchain**'s createAgent, whose loop runs the calls and calls the model again until it answers in text ([chat-model](chat-model.md)). Its agent prompt names a csv_to_json tool, the filesystem tools, and the MongoDB tools, and orders the steps: empty MongoDB, convert CSV to JSON, save the JSON when the intent asks, insert the records into a collection, query them to answer, and save the answer as a text report under reports. In the template, the tool list is empty and no node calls the agent. In the final version, csv_to_json converts CSV text with **csvtojson**, prints [getCSVToJSONTool] conversion result finished followed by the count and records, and answers the records as compact JSON, with every key in the header's order and every value a string. Every model answer with calls prints 🎯 Decided to call: and their names, and every call prints 🔧 Tool called:, its name, an arrow, and its arguments, then ✅ Tool done: and its result.

The safeguard lesson of module 2 hands the same createAgent every tool of the filesystem MCP server, whatever the user's role, under a system prompt that names none of them ([prompt-injection-defense](prompt-injection-defense.md)). Arguments that fail a tool's schema, such as null for read_text_file's optional head and tail, come back as a tool message that starts with Error invoking tool, names the tool, its arguments, and the error, and ends with Please fix the error and try again.

The Google Trends agent of module 3 turns a service into a tool. Its google_trends tool, made with **LangChain**'s tool helper and a **zod** schema, takes a list of keywords and answers compact JSON from a SerpApi service, and its description asks the model to call it whenever the user shares a video title idea. Both nodes of its graph offer it after the filesystem tools ([model-context-protocol](model-context-protocol.md)), and the researcher's prompt asks for exactly two keywords in a single call. The service prints 🔍 Fetching Google Trends data for keywords: and the list, then looks each keyword up in turn through the **serpapi** package, printing 🔍 Fetching data for and the keyword in quotes followed by three dots, and then 🔍 Fetched trends for, the quoted keyword, a colon, and the whole answer. Each lookup is GET /search on SerpApi with engine google_trends, the keyword as q, the key as api_key, date now 7-d, and data_type TIMESERIES. From the extracted values of the answer's timeline, a keyword gets its highest value as searchVolume, its average rounded half up as interestOverTime, and a trend that is rising when the average of the last three values is more than 1.2 times the average of the first three, declining when it is less than 0.8 times, and stable otherwise. A keyword whose answer has no timeline is left out, and so is one whose lookup fails, which prints ⚠️ Failed to fetch trends for, the quoted keyword, a colon, and the error to standard error. The tool answers the keywords sorted by interest from the highest, then relatedQueries and risingTopics, and the time of the answer in ISO 8601 UTC with milliseconds. Those two lists read the top and rising related queries and the rising related topics, which a TIMESERIES search never returns, so they are always empty. A configuration flag swaps the lookups for a fixture and a cache time is declared, but the lesson leaves the flag off and caches nothing.

The LangChain lesson of module 3 hands createAgent the five tools of the published customers server, then the fourteen of the filesystem server ([model-context-protocol](model-context-protocol.md)), and no tool of its own. Its system prompt describes a customer_operations intent and a general_question intent that no node sets, asks for answers in the user's language, JSON arrays when saving files, no confirmation before creating customers, and one more try after a failed call. Its question asks in Portuguese for three test customers, saved to ./data/users.json and then listed with the customers tool. The filesystem server resolves that relative path inside its allowed folder, data, so the file lands in data/data/users.json, after a first call fails when data/data does not exist yet. A call the server fails comes back to the model as a tool message that starts with ToolException: and ends with Please fix your mistakes., and the run goes on. Every call prints the same 🎯, 🔧, and ✅ lines as the multiple MCP tools lesson, the ✅ line with an empty tool name followed by the whole tool message.

OpsPilot defines its tools with **LangChain**'s tool helper and **zod** schemas over its store ([layered-architecture](layered-architecture.md)). Unit 2 has three, with short English descriptions:

- list_alerts takes a status of firing, resolved, or all, treating a missing or null status as firing, and answers a header such as Found 3 firing alert(s): followed by one line per alert with its id in brackets, its service, its severity, and its description separated by vertical bars, or No firing alerts found when there are none (No alerts found for all).
- open_incident takes a title, a service, and a severity of critical, high, medium, or low. Its description maps sev1 to sev4 onto the severities and asks for the exact service names of the request, and it answers five lines that start with Incident created successfully. ID: and then give the title, service, severity, and status.
- resolve_incident takes an id and answers three lines with the id, the service, and the resolution time in ISO 8601 UTC with milliseconds. An unknown id answers Error: Incident not found: and the id, as the tool's result.

Unit 3 treats the schema as prompt. It rewrites every description in Portuguese, saying when to use the tool, when not to, and which tool to use instead, describes every argument, and moves the severity aliases into the schema, which maps sev1 to sev4 onto the severities, ignoring case and surrounding spaces, before validating. The answers keep their texts, and three tools join them:

- list_incidents takes a status of open, resolved, or all, open when missing, and answers a header such as Found 1 open incident(s): followed by one line per incident with its id in brackets, title, service, severity, and status separated by vertical bars, plus a summary when there is one, or No open incidents found (No incidents found for all).
- consultar_runbook takes a service and answers Runbook for, the service, a colon, and the runbook on the next lines, or Error: Runbook not found: and the service.
- check_provider_status takes a provider, github by default or cloudflare, and reads that provider's public status page without a key. Each attempt waits at most 5 seconds, and a timeout, a network failure, or a 5xx answer gets one more attempt. A valid body, checked by **zod** with extra fields allowed, answers the provider, está, the indicator, a dash, and the description, as in github está none - All Systems Operational. Every failure is an answer too: a 4xx answers status page de github respondeu HTTP 404 without retrying, and anything else answers não consegui consultar o status de github, the detail in parentheses, and a sentence asking the model to rely on the internal alerts and warn the on-call engineer. Tests inject the fetch function.

The first three tools are also offered over MCP ([model-context-protocol](model-context-protocol.md)).

Unit 4 gives the chat agents a seventh tool, forget_preference, whose description says to use it when the on-call engineer asks to forget a preference or fact, and never to delete alerts or incidents, list memories, or handle one-off requests. It takes a query and deletes the current user's closest memory, answering with the fact it forgot ([semantic-memory](semantic-memory.md)). The arena and the bench keep six tools.

**LangGraph**'s prebuilt agent runs the loop ([state-graph](state-graph.md)). It runs every call of one model answer in order and returns one tool message per call, and arguments that fail the schema come back as a tool message saying Error: Received tool input did not match expected schema, followed by a line asking the model to fix its mistakes.

The AIOps labs of module 6 declare their tools with **CrewAI**'s tool decorator ([agent-crew](agent-crew.md)), whose argument names the tool. The function's docstring, trimmed at both ends with every later line's indentation kept, becomes the description, and its signature the parameters: strings or integers, each with a title and its default when it has one, all of them required, in a strict schema without additional properties. A tool answers text, and **CrewAI** turns any other value into text, so a dict reaches the model as **Python**'s repr, with single quotes. The tools over files, **Checkov**, and kubectl are in [infrastructure-as-code](infrastructure-as-code.md), and execute_terraform, which holds destructive commands for a password, in [agent-observability](agent-observability.md). The others answer fixed texts, choosing them by keywords in the lowercase argument:

- check_compliance_rules takes a query and answers Policy Rules: Prefix must be 'nexus-', region must be 'us-east-1', and S3 buckets must always be private.
- query_prometheus_metrics takes a query and answers 📊 Prometheus Result: Average latency at endpoint '/checkout' is 850ms (HIGH). P99 threshold exceeded. when it mentions latency, duration, or latência, else 📊 Prometheus Result: 5XX error rate is currently at 12% over the last 5 minutes. when it mentions error or taxa de erro, and otherwise 📊 Prometheus Result: Metrics are well within the normal baseline.
- query_jaeger_traces takes a service name and answers 🔍 Jaeger Trace: The performance bottleneck for service '<service>' is located in the database call to PostgreSQL (Span duration: 800ms).
- inspect_pod_failure takes a pod name. A name with api answers a block that starts with a line break and indents every line by eight spaces: EVENTS:, a BackOff warning, LOGS:, Error: Cannot connect to database at 10.0.1.5:5432, and DIAGNOSIS: Database connectivity failure (Network/Config). A name with worker answers STATUS: Terminated | REASON: OOMKilled | MEMORY_USAGE: 512Mi (Limit: 512Mi)., and any other Logs for Pod '<pod>' look normal, but the Readiness Probe is failing.
- suggest_fix takes an issue type and answers the fix for exactly OOMKilled, ImagePullBackOff, or CrashLoopBackOff, or Review the Readiness Probe and Liveness Probe configurations in the manifest. for anything else, such as a sentence that describes the issue.
- nl_to_promql takes a question and answers rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) when it mentions taxa de erro or error, else node_filesystem_avail_bytes{mountpoint="/data"} / node_filesystem_size_bytes{mountpoint="/data"} * 100 when it mentions disco or disk, and otherwise up{job="kubernetes-pods"}.
- predictive_disk_alert takes a metrics history and answers 🚨 [ALERTA PREDITIVO - MACHINE LEARNING] followed by three lines indented by eight spaces, the anomaly, the saturation in exactly 4 hours, and the recommended action, when it mentions growth or crescimento, and otherwise ✅ Padrão de uso normal. Sem anomalias na série temporal.
- generate_grafana_dashboard takes an incident context and writes incident_dashboard.json to the working directory: the title Dynamic Incident Dashboard: and the context, and two panels, Disk Usage Prediction, a timeseries of node_filesystem_avail_bytes, and Error Rate Spike, a stat of rate(http_requests_total{status='500'}[5m]), each query as an expr in a list of targets, indented by two spaces. It answers ✅ Dashboard gerado com sucesso! O arquivo 'incident_dashboard.json' foi salvo no disco pronto para importação no Grafana.
- The labs that read data/ answer the file's text, for the workflow and the runbook, or its parsed JSON, for the **Trivy** report and the cloud inventory.
- tools/governance_tools.py declares triage_security_vulnerabilities, optimize_cicd_pipeline, and analyze_finops_costs with fixed answers, but no program imports them, since the DevSecOps, CI/CD, and FinOps labs declare their own tools over data/, so no case reaches them.

The single-agent lesson of module 8 declares one tool in the OpenAI format for **Ollama**'s native chat, buscar_clausula_regulatoria, with a Portuguese description and two required arguments: a free-text tema and a jurisdicao of ANVISA or FDA. Its execution is deterministic and never raises. When either argument is missing or not a string, as when the model misspells jurisdicao, it answers texto and fonte null with an aviso that names the invalid call. Otherwise it matches tema by keyword after lowercasing, so ANVISA with a theme that mentions menor, adolescente, or pediátric answers the clause of RDC ANVISA 466/2012, Art. 4º, with that source as fonte, and anything else answers texto and fonte null with an aviso that suggests another jurisdiction or theme. The loop runs the first call of each answer and sends the observation back as JSON in a tool message that names the tool ([reasoning-strategies](reasoning-strategies.md)). The lesson's anatomy demo shows a smaller tool that takes a list of ages and finds the clause when any is under 18. A third file, provedores-pagos, declares the same tool for **Claude**, **Gemini**, and **GPT** through their SDKs ([llm-http-api](llm-http-api.md)) and maps each answer to a tool call, with tipo chamada_ferramenta, nome, and args, or to a final answer, with tipo resposta_final and texto. It only exports the three functions: Claude's and GPT's take the conversation, and Gemini's takes the protocol alone, because its Interactions API keeps the conversation on the server.

## What usually goes wrong in other languages

- Tool names, descriptions, argument enums, and, from unit 3, argument descriptions are part of the prompt. Transcriptions keep them verbatim, and the cases check them in every request.
- **zod** declares status as required in the JSON Schema while the tool accepts it missing. A **pydantic** default makes it optional instead, which the cases accept.
- The assistant message echoes each call's id, and each tool message carries the id of the call it answers. Real providers reject a conversation where they do not pair up, and the cases check the ids.
- Clients serialize the echoed arguments differently, **Python** with spaces after the separators, so the cases never compare argument strings.
- Several calls in one answer run in call order. **LangGraph** for **Python** runs synchronous tools in threads, so the tested transcription declares them as coroutines, which keeps incidents opened in one answer in order.
- **LangGraph** for **Python** reports pydantic's own text for invalid arguments and lets other tool errors escape, so the tested transcription passes an error handler that writes the original message.
- The original always reads the public status pages. Transcriptions read OPSPILOT_GITHUB_STATUS_URL and OPSPILOT_CLOUDFLARE_STATUS_URL first, as the copy that produced the cases does, so verification can serve recorded pages.
- A 4xx answer or an invalid body is final, and the cases count the status page requests. **Python**'s **httpx** and **requests** raise their own exception types for timeouts and connection errors, so a transcription maps each of them to a retry.
- A failed status check is the tool's answer, never an exception, so the model reads it and the run goes on. The detail of a 5xx is upstream and the status code, which the cases compare exactly.
- csv_to_json's answer reaches the model unchanged, and the cases compare it exactly. A transcription keeps the header's order instead of sorting the keys, as **Go**'s maps and **Python**'s sort_keys would, writes no spaces, and never converts the numbers.
- The **serpapi** package always calls https://serpapi.com. Transcriptions call SerpApi's HTTP API on /search themselves, reading the base address from SERPAPI_BASE_URL and falling back to https://serpapi.com, as the copy that produced the cases does, and the cases check the query parameters of each lookup, one keyword at a time in the model's order.
- The **serpapi** package refuses an empty key before sending anything, so the cases expect no lookup without a key. A failed lookup is a warning on standard error, never an error the model reads.
- interestOverTime rounds halves up, as **JavaScript**'s Math.round does. **Python**'s round and **C#**'s Math.Round round halves to even, so a transcription adds 0.5 and takes the floor.
- google_trends answers compact JSON with the keys in the order the code declares them, which the cases compare exactly apart from the timestamp, checked by its shape.
- Without a framework, the loop is written by hand: send the tools, run the calls, append the tool messages, and call the model again.
- createAgent checks a call's arguments against the tool's schema before the MCP server sees them. A client that forwards them unchecked, as the tested **Rust** transcription of the safeguard lesson does, sends the model the server's own error text instead, which the cases never compare.
- The LangChain lesson's committed data/users.json sits in data, while the filesystem server, at @latest and 2.0.1 when recorded, writes data/data/users.json. A transcription starts the same server through npx, and the cases expect the file where that server writes it.
- **LangChain** for **JavaScript** sends the model each MCP result as JSON holding its type, text, and structuredContent. The LangChain lesson's cases check each tool message by its call id alone and find the API's answers in the program's output, so a client that sends the text alone passes.
- **Ollama**'s native chat answers the arguments as an object and pairs a tool message with its call by tool_name, without ids. The OpenAI format answers them as a JSON string, which provedores-pagos parses, while **Claude**'s input and **Gemini**'s arguments arrive as objects.
- **CrewAI** marks every parameter as required, defaults included, and keeps the indentation of a docstring's later lines in the description, which the cases compare exactly. Answers written inside triple quotes keep their line breaks and leading spaces too.
- The cases check the values of a dict that a **CrewAI** tool returns in any notation, so a transcription may send JSON.
- **CrewAI** 1.14 runs every call of one answer, each in its own thread, and answers each with its own tool message. The cases of module 6's tools answer up to five calls at once, so a loop that runs only an answer's first call, as the single-agent lesson's does, fails them.
- Module 6's keyword tools test their keywords in order, so a query about the error rate and the latency answers the latency, a pod named api-worker the database failure, and a question about errors on a disk the error-rate query. inspect_pod_failure lowercases the name, while suggest_fix compares the issue type exactly, so oomkilled gets the generic advice.
- The single-agent tool reads its arguments as a map and checks each one, so a misspelled name becomes the tool's own failure. The **Python** version takes keyword arguments for the same reason, since fixed parameters would raise TypeError before the check, and prints the map inside the aviso as a repr where **JavaScript** prints JSON, which the cases accept.
- **Claude**'s Messages API takes no system role inside messages, so the single-agent loop's history, which starts with one, fails there with a 400. The cases call chamarClaude with the user message alone. **Claude** may write text before its tool_use block, so the call is found by its type, while the final answer reads the first block.

## How close common targets get

| Target                            | Fit               | Library                                                                   |
| --------------------------------- | ----------------- | ------------------------------------------------------------------------- |
| **Python**                        | Direct equivalent | **langchain-core** structured tools with **pydantic** argument models     |
| **JavaScript** and **TypeScript** | Direct equivalent | **@langchain/core** tools with **zod** schemas                            |
| **Java**                          | Direct equivalent | **LangChain4j** tools                                                     |
| **Go**                            | Substitute        | **openai-go** function definitions, with the loop written by hand         |
| **Rust**                          | Substitute        | **async-openai** with **schemars** for the schemas and the loop by hand   |
| **C#**                            | Substitute        | The official **OpenAI** library for .NET, with the loop written by hand   |
| **C++**                           | Substitute        | **nlohmann/json** schemas over **libcurl**, with the loop written by hand |
