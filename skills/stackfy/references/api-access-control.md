# API access control

## Concept

Before an API runs a route, it answers three questions: who is calling (authentication), whether that caller may do this (authorization), and whether it has called too often (rate limiting). Programs prove who they are with a bearer token, sent on every request as Authorization: Bearer followed by the token. A JSON Web Token (JWT) carries its claims, such as the user and the role, in a payload signed with the server's secret, so the server verifies the signature and trusts the claims without a lookup. An opaque token is a random value the server issued and stored with its owner, so the server looks it up on every request. A missing, forged, or unknown token answers 401, a known caller whose role does not allow the action answers 403, and a caller past its number of requests in the window answers 429, often with headers that give the limit, what remains, and when the window resets. The client keeps its token outside the code, sends it on every call, and tells these answers apart, since only a 429 is worth trying again later. Signing a person into a browser session through an identity provider is [user-authentication](user-authentication.md), and this concept guards the API itself.

## How the course implements it

The API security lesson of module 3 secures the legacy customers API ([rest-api](rest-api.md)) and the MCP server in front of it ([model-context-protocol](model-context-protocol.md)). Its template moves the API to **Fastify** 5 and the **mongodb** driver 7 ([document-database](document-database.md)) and declares **@fastify/jwt** 10 and **@fastify/rate-limit** 10, but only imports the first and registers neither. It keeps two users in a list of its own, erickwendel with the password 123123 as admin and ananeri with 1234 as member, and exports a limit of 90 requests per minute that nothing reads yet. So the template still serves every route to anyone, ignores any Authorization header, sends no rate limit headers, and answers the login and service token routes with **Fastify**'s 404. Its tests for logins, service tokens, roles, and the limit are skipped, and its README describes the API as the final version secures it.

The template's MCP server is already a client of that secured API. It refuses to start without SERVICE_TOKEN, printing [error]: SERVICE_TOKEN env var is required to standard error and exiting 1, and its HTTP client sends the token as a bearer on every call to http://localhost:9999/v1. It turns a 401 into the error Unauthorized: service token is missing or invalid, a 403 into Forbidden: token does not have sufficient permissions, a 429 into Rate limit exceeded. Please try again later., and any other failing status into HTTP, the status, its text, and the body as the API wrote it, joined by spaced dashes, as in HTTP 404 - Not Found - followed by the body. A lookup by \_id still reads a 404 or a 400 as no customer. Every tool catches the error and answers Failed to, its action (list customers, find customer, create customer, update customer, or delete customer), . Error:, and the error's message, both as the text and as the message of a structuredContent whose isError is true, while the result's own isError stays unset. Its getServiceToken.sh asks the secured API for the admin's and the member's service tokens, and its .vscode/mcp.json passes a fixed one. The final version's MCP server is the same, apart from the token its .vscode/mcp.json passes and the name and version of its package.json, now the ones the server announces. The publishing lesson keeps the final version's API and MCP server, apart from that token and the package the server ships as ([package-publishing](package-publishing.md)).

The LangChain lesson of module 3 runs the same API for an agent that starts the published server with SERVICE_TOKEN from its own environment ([model-context-protocol](model-context-protocol.md)), and refuses to build the server's configuration without it. Its getServiceToken.sh posts the admin's credentials and the adminSuperSecret as JSON to http://localhost:9999/v1/auth/service-token with curl --silent, reads serviceToken from the answer with jq -r, and prints nothing. When .env has a line that starts with SERVICE_TOKEN=, it replaces that whole line in place with sed -i '' and keeps every other line, a missing final newline included, and otherwise it appends SERVICE_TOKEN= and the token as a new line, creating .env when there is none.

The final version registers **@fastify/jwt** with the secret supersecret and **@fastify/rate-limit** at 90 requests a minute, although its README says 3. A hook on every request lets through only /v1/health, /v1/auth/login, and /v1/auth/service-token, whatever the method, compared with the whole address, query included. Every other request needs a service token the server issued or a JWT it signed, or it answers 401 with {"message":"Unauthorized"} before anything else runs, unknown routes and CORS preflights included, without CORS or rate limit headers. The hook removes the first bearer and space from the Authorization header, in any case, and looks the rest up among its service tokens, so a service token also passes alone, while a JWT must follow Bearer, in any case. Login takes a username, compared without case, and a password, and answers an HS256 JWT whose payload holds the username as it came, the role, and iat, with no expiry. The server trusts those claims without looking the user up, so any JWT signed with the secret passes, whoever it names, while one signed with another secret, an expired one, or one whose algorithm is none answers 401. The service token route also requires the adminSuperSecret AM I THE BOSS?, checked before the credentials, and answers the role and a random UUID that the server keeps in memory until it stops, so the token a .vscode/mcp.json holds lasts only as long as the API that issued it. Every request past the hook counts toward the limit, refusals included, under the Authorization header without its bearer, or under the caller's address when there is none, so the health, the login, and the service token route share one count per address. A counted answer carries x-ratelimit-limit, x-ratelimit-remaining, and x-ratelimit-reset, the seconds left in a fixed window that starts with the key's first request, and the request after the 90th answers 429 with **@fastify/rate-limit**'s body, {"statusCode":429,"error":"Too Many Requests","message":"Rate limit exceeded, retry in 1 minute"}, whose wait later reads in seconds, a retry-after, and no CORS headers. Only then is the body checked against its schema, the CORS headers added, and the role compared: creating, updating, and deleting require exactly admin, or answer 403 with {"message":"Forbidden: insufficient permissions"}, so a member's write without a phone answers 400, not 403. With a valid token, an unknown route answers **Fastify**'s 404 and a preflight answers empty with the CORS headers, neither counted. The tests the template skips run in the final version.

## What usually goes wrong in other languages

- A transcription of the template's API that registers a JWT check or a rate limiter fails its cases, which expect the login route to be unknown, a token to change nothing, and no rate limit headers.
- The MCP server reads SERVICE_TOKEN before it connects and exits 1 when it is empty, so a transcription that reads it on the first call never prints the error.
- Every call carries Authorization: Bearer and the token, reads included. The cases' recorded answers require that header, so a call without it gets no answer the original would get.
- The error names the status's reason phrase, as **Node.js**'s fetch reports it. **Go**'s Response.Status already starts with the code, so a transcription writes http.StatusText instead, **Java**'s HttpClient keeps no reason phrase at all and needs a table of its own, and **Rust**'s reqwest gives canonical_reason, **Python**'s urllib the reason, and **C#** the ReasonPhrase.
- The body goes into the message as the API wrote it. Decoding and encoding it again changes its spacing or its key order, and the cases compare the whole message.
- 401, 403, and 429 are checked before any other failing status, and a lookup by \_id returns no customer for 404 and 400 before checking the rest, so a 401 during a lookup is an error, not a missing customer.
- A refusal is an ordinary result that holds isError inside structuredContent. Raising it as an exception, as **Go**'s go-sdk, FastMCP's ToolError, or **rmcp** would, sets the result's own isError and drops the structured message.
- The original never retries. Clients configured to retry a 429, such as **urllib3**'s Retry, **Polly**, or a retrying **Go** transport, make calls the cases do not expect.
- The final API decides in a fixed order: the token (401), the limit (429), the body (400), and the role (403). A framework's authorization attribute or role guard that runs before validation answers a member's invalid write with 403, and a rate limiter placed before authentication counts the 401s.
- Its login's JWT has no exp. **Rust**'s **jsonwebtoken** requires exp by default, skips nbf, and allows a minute of leeway, so its Validation needs an empty list of required claims, nbf turned on, and no leeway, while **PyJWT** and **golang-jwt** check exp and nbf only when present. Every library must be told the algorithm, so a token whose algorithm is none never passes.
- The service token is found by removing the first bearer and space in any case, not by parsing the scheme, so a strict Bearer parser refuses the lowercase scheme and the bare service token that the original accepts.
- A rate limiter keyed only by address, as most frameworks' defaults are, merges every token behind one address, and one that skips the public routes leaves the login open to unlimited guesses.
- **@fastify/rate-limit** counts requests in a fixed window that resets a minute after the first one, while token buckets such as **Go**'s golang.org/x/time/rate or **Rust**'s **governor** refill gradually and let requests through earlier.
- The LangChain lesson's getServiceToken.sh replaces the line with sed -i '', the in-place form of BSD sed on macOS, which GNU sed reads as a script and fails, so on Linux the line needs sed -i alone, and other targets rewrite the file themselves. Appending to a .env whose last line lacks a newline joins the token to that line.
- A refused request makes jq write null, and an unreachable API leaves the token empty, and the script still writes the line, so a transcription that fails instead changes what the student gets.

## How close common targets get

| Target                            | Fit               | Library                                                                                           |
| --------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------- |
| **JavaScript** and **TypeScript** | Direct equivalent | **@fastify/jwt** and **@fastify/rate-limit** on **Fastify**, and fetch for the client             |
| **Python**                        | Direct equivalent | **PyJWT** with a fixed window counted by hand, and urllib.request for the client                  |
| **Go**                            | Direct equivalent | **golang-jwt** with a fixed window counted by hand, and net/http for the client                   |
| **Rust**                          | Direct equivalent | **jsonwebtoken** with a fixed window counted by hand, and **reqwest** for the client              |
| **C#**                            | Direct equivalent | ASP.NET Core's JWT bearer authentication and fixed window rate limiter, and HttpClient            |
| **Java**                          | Direct equivalent | **java-jwt** with **Bucket4j** set to refill the whole window at once, and the JDK's HttpClient   |
| **C++**                           | Direct equivalent | **jwt-cpp** on **OpenSSL** with a fixed window counted by hand, and **cpp-httplib** as the client |

A fixed window is one counter and one start time per key, so most targets count it by hand rather than take a token bucket that refills gradually. The tested **Python** transcription of the template's MCP server, a client that sends its token and turns every refusal into a structured error, and the tested **Rust** transcription of the final version's API, with **axum**, **jsonwebtoken**, and a fixed window counted by hand, sit with the api-access-control examples.

## Tolerance

The MCP cases replay the customers API on port 9999 instead of running it, so their ObjectIds are fixed and every answer is compared exactly, with texts that hold JSON compared by value. The template's customers' answers were recorded from the template's API and its refusals from the final version's API, while the final version's and the publishing lesson's were all recorded from each lesson's own API, with the service tokens it issued. The refusals come with an unknown token, a member's service token, and an admin's that had spent its 90 requests. The template API's cases check ObjectIds by shape and the absence of rate limit headers as empty values. The LangChain lesson's cases replay the service token route and the customers API on port 9999 with answers recorded from its own API, so the token is the one it issued, its .env is compared exactly, and every customers answer requires that token as a bearer.

The final API's cases, which the publishing and LangChain lessons' APIs share, run it on an empty **MongoDB** and check the JWTs and service tokens it issues by shape before sending them back. They also send JWTs signed by hand with a fixed iat, so a transcription must use HS256 with the secret supersecret. The rate limit headers are compared exactly, apart from x-ratelimit-reset and retry-after, which count down from 60, and the 429's wait, which reads 1 minute or a number of seconds. The cases spend 90 requests by repeating one request, and the runner's readiness check on /v1/health counts toward its address, so they never compare that address's count exactly.
